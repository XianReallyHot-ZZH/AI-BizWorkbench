## 1. 讲解

### 1.1 本讲要什么

L09 把失败报告翻译成修复任务，L10 把「检查→修复→再检查」组织成有停止条件的纵向重复，L11 把独立子任务横向并行。交付还剩一类去向没有显式化：**检查通过后要等人（等待）、审核打回要返回修改（回退）、程序重启要从可靠位置继续（恢复）**。Graph 把「当前在哪个节点、什么条件下去哪里」写成可执行规则——节点管当前做什么，边管允许去哪（没有「修改→完成」这条边就不能跳过检查与审核），条件管此刻能否走（条件来自可核对的数据，不来自模型说"应该没问题"），共享状态管沿途事实（不是全部聊天内容），Trace 记录实际走过的路。**Graph 是允许路线，Trace 是实际路线，两者不同**——轨迹写了 develop，还要能找到实际执行与 Diff；标签只能证明记录存在，不能单独证明动作发生。

上游钉死的判断，本讲全链贯穿：**等待是正确结果不是失败**（退出码 3 ≠ 检查失败）；**打回后形成新候选必须重新检查**（X 的报告与接受状态不能沿用给 Y）；**完成是终态，重读不重执行**；**异常显式进入失败态，不被静默吞掉**；**状态名只是位置，动作结果才是推进依据**。

### 1.2 业务案例：审批后入库——两种批准不能互替（PURCHASE:COURSE-DEMO / SKU:COURSE-DEMO）

教学数据（手册口径，SKU 用上游 lab 的 `A`）：A 在库 10，OTHER 已预占 2（可用 8），另有既有申请 PR-OTHER（A×3）。主线四拍：①PR-TARGET（A×7，理由「补货」）保存为 proposed——三量仍 10/2/8；②采购负责人具名批准 → approved，**库存仍 10/2/8**（批准的是业务单据，不是货已到）；③收到 7 件登记入库（业务键 `receipt:target`）→ received + 17/2/15 + 一条 +7 流水；④同键重试 → 五表不变（幂等）。失败路径：未批准 / 已拒绝请求入库 → ApprovalRequired 且五表不变；审批人空白 → ValueError 且五表不变；已入库后换键再请求 → InvalidTransition 且五表不变。

**软件审核 ≠ 采购批准**（本讲核心区分）：前者决定软件候选 Y 能否交付（对象 = 候选 + 报告），后者决定采购单 PR-TARGET 能否执行（对象 = 业务单据）。软件全绿不能替采购批准，另一张 PR-OTHER 的批准也不能授权 PR-TARGET；即使同一个人承担两种职责，也要分开记录对象与理由。

**故障与恢复**（上游实验如实暴露，上游明示「本次未修复产品代码」）：`status-write-failure` 模式用教学触发器阻止单据改 received——事实是**库存已 +7 提交、单据仍 approved**（`receive_stock` 与状态翻转是两个事务——部分提交），原子性断言红；`recovery-same-key` 模式移除触发器后**用原键重试**——补齐单据状态且不重复加库存（同键重放安全），但**恢复成功不能证明第一次操作具有原子性**；`key-collision` 模式用已被期初入库消费的 `opening` 键请求入库——**单据 received 但库存仍 10、无 +7 流水**（已消费键静默吞掉入库：失败显示成成功，业务边界 5 的客户面活教材），状态对账断言红。这三个真实失败保留供学习，恰与 L11 乙子代理 R1/R4 实证互证（§1.3 第 5 条）。

### 1.3 客户真理现查（讲前 2026-10-02，`vendors/flowERP` submodule 只读）

1. **审批面在场且正确**：`flowerp/service.py:340` `approve_purchase`——`:341-342` 空审批人 ValueError；`:347-348` 非 proposed → InvalidTransition；`:349-352` UPDATE approved + 具名 `approved_by`。`:355` `reject_purchase` 同形（proposed → rejected；乙观察原样：rejected_by 写进 `approved_by` 列 `:365`，靠 status 列区分语义，如实记录不改）；
2. **入库面在场：幂等与守卫正确，两段事务是原样行为**：`:386` `receive_purchase`——`:388-396` received 分支（同键重放返 `idempotent_replay` / 异键 InvalidTransition）；`:397-398` ApprovalRequired 守卫（**acceptance[0] 直接对应**）；`:399` `receive_stock`（自带事务提交库存+事件）与 `:400-404` 状态翻转（第二个事务）之间无原子性——**R1 两段事务窗口**。`receive_stock :150`——`:157-165` 键存在即重放返回快照（`idempotent_replay: true`），**不校验键与 sku/quantity/reference 的一致性**（R4 已消费键静默吞的根源）；`:166-170` 事件 INSERT 与库存 UPDATE 同事务（单事务内无部分写入）；

5. **R1–R6（L11 乙子代理移交，本讲处置口径见 D5）**：R1 两段事务窗口 / R2 换键重驱双入（并发窗口，正常序列测不出）/ R3 event_key=None 绕过 / R4 已消费键静默吞 / R5 双事件重放误拒——全部已证实且全部位于 `receive_purchase→receive_stock` 段（= 本讲业务增量面）；R6 `_publish_authority` 事务外（待验证，乙未复现）。**这些是客户真理的原样行为（上游参考实现同形），不是本讲复刻的缺陷**——本讲以探针实证钉住 R1（status-write-failure）/ R4（key-collision）两件必红选跑，其余引用乙发现如实标注不复现；
6. **分层边界（如实记录）**：辅导资料明示 `agent/graph.py` 是最小观察支架（develop 节点未调用 Codex、传入姓名不认证身份、批准未绑定候选——stale-approval 反例如实暴露、`move` 未验边），`workbench/workflow_graph.py` 是另一层持久化治理——两层不能混称，参考支架的局限不等于整个工作台缺失这些能力；本讲交付 `agent/` 对应物，治理层不在本讲范围；

**结论**：本讲增量如实转为——①**Graph 控制器 Java 对应物**（`agent/graph.py` → `workbench/graph/` + REGISTRY `graph-run`，agent 家族第四件收齐）；②**审批入库面探针与统一入口**（九模式探针驱动客户真身 + 登记项收口含两绑定 eval）；③**故障与恢复实证**（部分提交 / 键冲突两必红选跑 + 同键恢复——R1/R4 对照账）；④**Graph×ERP 对账证据链**（真实检查走通等待→具名批准→完成，状态文件 × 五表快照对账表——acceptance[2] 承载）。
