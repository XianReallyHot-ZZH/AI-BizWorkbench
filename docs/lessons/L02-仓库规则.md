# L02 - 仓库规则

> 延伸阅读（上游原讲义）：`vendors/CodexFDE/docs/courses/L02/`（README / 辅导资料 / 实践操作手册 / 行动卡 / `write-agents/` 写规则 Skill）。上游标题"把仓库规则写进 `AGENTS.md`"。原讲义口径为 Windows PowerShell + Codex CLI + 新建 Codex 任务做前后对照；本讲义为 macOS + Claude Code + `claude -p` 无头对照 + `lesson-02` 候选分支（ADR-0004）口径。对照基线 `CodexFDE@a74445a`（检查点 0001：2026-09-27 用户裁决从 58f4612 升级；冻结合同无变化）。

## 1. 讲解

L01 的工作台能记账了，但跨会话协作仍靠口头重申：哪些文件能改、什么结果不能写成"已验收"、做完必须交回什么。本讲把这些**已确认的约定**固化进仓库根目录的规则文件，再用全新会话做 N0/N1 前后对照，证明规则真的被读取、真的改变行为——不是写了就算。核心纪律沿用上游：**先保留修改前的回答 N0，再写规则**；边改边测，最后就说不清差别从哪里来。

**规则文件口径（本讲第一个显式决策，随讲义一并裁决）**：上游写 `AGENTS.md`（Codex 生态惯例）；本仓库执行器是 Claude Code（ADR-0002），原生规则文件是 `CLAUDE.md` 且**已存在**（6b38970，内容为复刻协作指南）。同形映射：**`AGENTS.md` → `CLAUDE.md`**——在已有规则文件上做增量补齐，正好复现上游"已有规则先保留修改前副本，再补缺失内容"的练习场景。冻结合同 fixture 的 `write_scope=("AGENTS.md", "tests/")` 逐字不动，映射记入 §2 口径注。

规则内容回答上游四问：**去哪里改**（目录职责与调用方向）、**什么不能随意改变**（禁止事项）、**怎样检查**（真实验证命令）、**怎样算完成**（Definition of Done）。其中本仓库已具备：铁律六条（待审核 ≠ 已接受、vendors 只读、证据纪律等）与常用命令；**缺失**的是——五条 FlowERP 业务不变量、结构调用方向约定、完成定义。这三块就是本讲增量，也是起始红的落点。

五条业务边界逐字承自上游（为 L04+ 工作台驱动 flowERP 预埋边界，加适用条件"涉及 FlowERP 业务实现时"）：可用库存不能为负、预占必须原子化；同一个入库幂等键只能生效一次；订单只能按状态机迁移、取消时释放预占；采购补货必须由具名人员批准后才能入库；任务、Eval 和反馈必须可追溯，失败不能显示成成功。

**验证规则是否有用要三层分检**（上游辅导资料 §5）：规则有没有进入会话（N1 引用条款）、回答是否遵守规则（五条越界判拒 + 合法维护放行）、程序检查结果如何（unittest 回归）。三者互不替代：文本在场 ≠ 行为遵守，程序绿 ≠ 规则生效。

N0/N1 的执行器映射：上游"新建一个干净的 Codex 任务"→ 本复刻用 `claude -p` 无头会话（新进程、干净上下文、stdout 即完整回答，天然可留证）。固定请求逐字承自上游手册，仅词面适配（AGENTS.md → 规则文件）。**N0 可以正确**——本仓库 CLAUDE.md 已有"待审核 ≠ 已接受"铁律，固定请求第 5 条可能本来就答对；此时如实记录"没有观察到明显行为改善，但新任务已正确引用规则"，不制造失败。

因果交接：本讲固化的是**长期规则**（跨任务有效）；L03 的六段式 Spec 是**单次合同**（一次需求签字即冻结）——长期规则管"永远怎样"，Spec 管"这次要什么"，L04 换挡点后执行器在两者划定的边界内受控交付。本讲不接入 FlowERP、不实现 eval.harness（冻结合同 `evals=()`，本讲无绑定 Eval）。
