## 1. 讲解

### 1.1 本讲要什么

L08 交付的是**可信红报告 + 候选身份**（B Run 的红灯：检查发现失败、退出码诚实传播）。L09 接过这份红灯问下一个问题：**"报告里有一个红灯"还不是可以委托执行器的任务**——哪里能改（允许写集）、怎样复现（复现命令）、修好后应看到什么（验收命令）、谁确认过（human_review），都要说清。把这些从"人的现场判断"变成工作台的确定性翻译，就是本讲的映射器：**报告字节 + 已确认上下文 → Repair Task 草案**，不是根因猜测器，也不扩大授权。

本讲两个增量**分开走**（上游核心教学点）：先建工作台映射能力（workbench_increment），再用它组织一次取消修复（erp_increment）——前者验"工作单生成得对不对"，后者验"订单行为恢复没恢复"，各自留结果。这就是上游的 AI4AI 现场含义：用 AI 帮助建设组织 AI 工作的能力，且新能力必须被真实使用过一次才算建成（生成器存在但没有被后续执行使用，只完成了一半）。上游 legacy 映射器 `build_repair_task` 的六个洞（空对象生成空任务、缺 passed 被选中、字符串 "false" 被漏选、缺 evidence 崩溃、指令文本被复制、混合报告不分级）是本讲严格版的设计反例——六模式机检（C5）就是把这些洞逐一堵上并证明。

### 1.2 业务案例：取消释放预占（入门 ERPService 主线）

双商品双单教学数据（手册口径）：在库 A=10、B=8；TARGET 预占 A4/B3，OTHER 预占 A2/B1；当前可用 A4/B4。取消 TARGET 的正确结果：**总预占 A2/B1、可用 A8/B7、在库不变、OTHER 不变**，且释放流水（inventory_events 的 release 行）归属 TARGET。教学错误写法（辅导资料）：先改状态再判断——`status = "cancelled"` 之后再判 `if status == "reserved"`，释放分支被跳过；正确修复是**用原状态决定释放、释放与状态变更放同一事务**。观察面是**四张表**（stock / sales_orders / sales_order_lines / inventory_events），不能只看错误消息或订单状态。

四条路径都要有裁判（上游 cancellation_lab 六模式收敛为五 + 注入态）：正常取消（释放完整）；草稿取消（无预占无释放事件）；重复取消（参考合同拒绝，且拒绝后四表不变）；已发货拒绝（InvalidTransition）；中途写入失败（write-error 触发器注入第二条释放事件写入故障——事务性区分器：失败后四表回滚无半成品）。leak 数据面注入（临时库直接 UPDATE 状态跳过释放）只作教学对照——**仅切换数据不构成修复**，完整修复链必须有代码 Diff（1.4 映射）。

### 1.3 客户真理现查（讲前 2026-10-01，`vendors/flowERP` submodule 只读）
