## 1. 讲解

### 1.1 本讲要什么

L09 交付报告→修复任务的映射，L10 把「检查→修复→再检查」组织成**有停止条件的纵向重复**（Loop）。L11 换一个轴：**独立任务的横向分工**——把一项交付拆成互不冲突的子任务并行执行，再由主 Agent 串行集成、同版复验。Loop 管「同一件事何时停」，Subagents 管「不同的事能否同时做」。

**独立性判定的文件面**（上游钉死，全讲沿用）：读集 R 是任务依赖的文件，写集 W 是任务会修改的文件；两项任务声明独立需**三个交集都为空**——`W甲∩W乙`（不互相覆盖）、`W甲∩R乙`、`W乙∩R甲`（互不改变对方依据）；**读读共享允许**。交集含目录覆盖（写 `flowerp/` 即覆盖其中的 `service.py`）与路径别名（反斜杠、大小写、`./` 前缀）。文件之外还有**共享运行资源**（同一数据库、报告路径、端口）与**语义依赖**（单位、接口含义）——声明检查器只查声明路径，`undeclared-read` 漏报读取照样返回 allowed：**声明通过 ≠ 执行安全**（上游教学反例，判断留给整合层）。

上游钉死的三个判断，本讲全链贯穿：**能同时启动，不等于任务独立；局部通过，不等于整合通过；子任务更快，不等于完整交付更快**。并行总耗时 = 准备启动 + 最慢子任务 + 汇总返工复验（教学算例：串行 18 vs 并行 19 分钟——委派 2 + 等待 8 + 汇总 5 + 复验 4；另一算例 25 vs 20，返工 7 分钟即反转）；未做单 Agent 对照实测时不声称提效（挑战任务边界，如实保留缺项）。

### 1.2 业务案例：采购申请——保存意图，不提前入库（PURCHASE:COURSE-DEMO）

教学数据（手册口径）：A 在库 10，OTHER 已预占 2（可用 8），另有既有申请 PR-OTHER。创建 PR-TARGET（A×7，理由「低于补货点」）：校验（数量 >0、原因非空白）、SKU 规范化（`a`→`A`）、理由去首尾空白，保存一张 **proposed** 申请可按编号再查；**申请 ≠ 收货**——三量仍 10/2/8，库存流水、OTHER、PR-OTHER 不变。把「提出想买」和「已经到货」分开，是本讲实现与所有检查的共同依据。

失败路径五拍（上游实验全口径；合同 acceptance[2]「非法数量」为其子集）：零数量 / 负数量（ValueError）、空白原因（ValueError）、未知 SKU（NotFound）、重复编号（`sqlite3.IntegrityError`）——拒绝后**五表不变**（purchase_requests / stock / inventory_events / sales_orders / sales_order_lines）；只查「抛异常」不够，可能先写入部分数据才报错。**重复编号语义如实**：数据库唯一性冲突，不是幂等返回原成功结果（上游钉死，不得改写）。

教学缺陷 `premature-stock`：申请保存后人为追加一次 `receive_stock`——申请字段仍全对（原检查 `purchase_request_preserves_reason` 照样绿），但库存变 17/2/15 且多一条入库流水，独立库存不变检查红。这就是「**同版不同覆盖**」：两份报告服务指纹相同、检查内容不同，可同时成立——主 Agent 不能投票或平均通过率，只能回查覆盖范围、定位动作、串行移除、修复后同版复验（V1 报告留史，不替 V2 作证）。
