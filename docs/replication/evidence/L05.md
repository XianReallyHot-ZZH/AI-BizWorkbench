## 6. 口径与限制

- **同命令异树口径（C4，逐字披露）**：红绿两条记录的 `command_text` 为逐字节相同命令串；目标树差异经环境变量 `L05_EVAL_TARGET` 注入（红=缺陷基线，绿=真实候选），由输出内 `pwd` 行、封存 `meta.json` 的 argv 与本账三重披露。链判定的"同命令"语义（同一检查、先红后绿）在"同一检查命令、缺陷树红/正确树绿"上成立——这是本讲增量重定位（D1）的设计本意，非账面技巧。
- **失败信息定位口径（C3）**：客户 eval 为裸 `assert`（无消息文本），不能改它加消息（改即违 D1"不重写客户检查"）；定位 = 用例名 `receiving_is_idempotent` + 失败断言 `second["on_hand"] == 5`（traceback 行）+ `[BLOCK]` 行，映射 FlowERP 边界 #2（同一个入库幂等键只能生效一次）。上游通过标准"失败信息能够定位到具体要求"以此映射满足。
- **驱动身份口径（D4）**：`receiving_scenario_check.py` 是 observing 补充（C6/C7），**不冒充** blocking 身份；blocking 身份恒为客户用例 `receiving_is_idempotent`（冻结指纹内）。
- **缺陷基线口径（D2/R2）**：基线仅存在于 `.runtime/course/L05-defect-baseline/`（gitignored，永不合入）；构造可复现（`evals/l05/build_defect_baseline.py`，锚点守卫）。候选分支内产品 diff 为空——客户已实现幂等，本讲不做"实现幂等"的伪交付。
- **盲区边界（C7，如实）**：客户 eval 不读 `inventory_events` 流水，对"账面重写"类缺陷盲（实证）；并发、进程崩溃、同键不同内容三类边界本讲未覆盖，上游同口径（"本讲的顺序调用实验不自动覆盖"）。是否补流水断言属改客户检查，留待检查点显式采纳（ADR-0003），本讲不动客户文件。
- **tdd 技能口径**：本讲 D3 钉死 workbench 零新命令 → 无 unittest 起始红缝；红绿纪律（红先于绿、同命令、断言不放宽）经客户 eval 链体现（record 44→48），未走 `tdd` 技能的 unittest 流程，如实声明。
- **vendors 双查**：本讲全程 `git -C vendors/CodexFDE status --short` 与 flowERP 同查恒空（clone 只读源，缺陷只落在 `.runtime/` clone）。
- `acceptance: pending_human_review` 恒待人签；**待审核 ≠ 已接受**。
