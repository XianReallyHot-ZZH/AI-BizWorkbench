## Problem Statement

交付链在 L13/L14 已能受理、执行、投影，但**经验仍然是一次性的**：使用者对交付提出反馈后，反馈只是一条 pending 记录——没有审核闸门挡住「原始反馈直接变成执行依据」，也没有通道把「这次踩的坑」变成下次能检索到的带引用上下文；支线 S01 在 Python 时代建成过七命令记忆闭环，但那套实现已随 ADR-0006 退役封存（tag `python-carrier-final`），Java 线（当前唯一活动实现）没有对应物——每次会话都在「裸脑」开工；L14 面板预埋的 evolution 块与 verified_evolutions 计数仍是欠账（D4 裁掉时的明示缺口）；课程合同在本讲首次要求 `dynamic_eval_required=true`——本次需求新增的 Eval 用例必须先真实失败，而工作台没有承载这个「起始红形式化」的机制；ERP 侧 L11/L12 对照账已运行实证两起客户原样缺陷（R1 两段事务窗口部分提交 / R4 已消费幂等键静默吞），它们是真实的使用者反馈，但「反馈→改进→升级前后证据」的治理链不存在。合同验收三条（原始反馈先审核再进入记忆候选与执行合同 / 记忆来源、版本、状态、检索结果、采用快照和后续验证可追溯 / 撤回或跨项目记忆不进入默认上下文，反馈与检索结果均不能直接改写阻断裁判）全部指向同一个不可妥协点：**经验可以被治理，但不能被绕过治理**。

## User Stories

1. 作为使用者，我想对已交付事项提出结构化反馈（来源 + 结论 + 下一步 + 可选证据），以便我的真实痛点以 FB-* 身份入账待审而不是口头流失。
2. 作为使用者，我想让交付失败被自动沉淀为待审观察反馈（pending_review，source=automation:*，失败签名去重），以便失败经验不靠人记（L13 已建面，本讲复验）。
3. 作为具名审核人，我想对反馈 accept/reject（具名 + 决定 + 备注），以便「这条反馈值得立项」是人的判断且不可被重复改写（已审核再决定被拒）。
4. 作为使用者，我想让未审核反馈被任何通道提升为进化记录时遭到拒绝（词面「只有具名接受的反馈才能提升为进化记录」），以便原始反馈永远不能直接变成执行依据（合同 acceptance[0]）。
5. 作为使用者，我想让反馈被接受后 EVALS 里的阻断用例（如 receiving_is_idempotent）仍是 blocking，以便「接受也不等于改写当前 blocking 裁判」（合同 acceptance[2] 后半）。
6. 作为改进发起人，我想从已接受反馈创建进化候选（失败签名 ≤200 + 五分类 + business_refs ≥1 不重复），以便立项有结构化因果链（feedback_id → 源任务 → 业务对象）。
7. 作为具名审核人，我想对进化候选 approve/reject/defer（具名 + 理由必填，只 proposed 可决定），以便立项本身也过人审闸门。
8. 作为改进执行者，我想在 approved 后登记版本化资产变化（type ∈ 七类 + path + reason，同 type+path 去重，≤20 项），以便「这次改进动了什么」可枚举可追溯。
9. 作为改进执行者，我想让 verify 重门全数生效（候选任务 ≠ 源任务、共享 business_ref、晚于进化创建、completed + 具名 approve + decision pass + blocking_failed 0 + 逐项 blocking 通过 + 报告在受控 reports 目录且 sha256 重算一致），以便「升级有效」由下一项独立交付任务的不可替换证据背书，不能自证。
10. 作为改进执行者，我想让登记为 learning/ 资产的进化在 verify 时强制核对实际版本采用（候选任务有绑定 + outcome passed + 登记资产 ⊆ 采用集），以便「写进记忆的经验」必须被真的用过且复验通过（governed 分支）。
11. 作为审计者，我想让同一反馈只能形成一条进化记录、非法状态迁移（proposed 之外 review、asset_changed 之外 verify 等）被拒，以便进化账不重不乱。
12. 作为审计者，我想让每次进化状态迁移都落事件（from/to/detail/actor/evidence），以便演进过程可回放。
13. 作为经验提炼者，我想从已验收任务提炼记忆候选（来源快照整体封存记 sha256——任务事实 + 复核 + 执行摘要引用），以便「已审核经验」四个字有证据背书（合同 acceptance[1] 来源可追溯）。
14. 作为经验提炼者，我想从已接受失败反馈对应的 Evolution 提炼失败经验（source_task_id 一致 + 非 rejected/deferred + 失败轨迹在场——error 或事件含 rework/failed/dead_letter），以便踩过的坑也能变成可复用记忆（L15 新来源入口）。
15. 作为经验提炼者，我想让只给 feedback_id 的提炼自动级联建进化（走同一道审核门），以便入口可以有捷径但闸门没有捷径。
16. 作为具名治理人，我想 approve/publish/revoke 记忆条目（human() 门拒 ai/codex/system/claude/待确认/待定/tbd/pending/agent:*，且不得是提炼者——S01 口径），以便记忆进默认上下文前必须过具名人工（合同 acceptance[0] 记忆候选闸门）。
17. 作为具名治理人，我想让跳过审批的 publish 被拒、revoked 再 revoke 被拒，以便治理状态机与进化状态机一样不重不乱。
18. 作为经验发布者，我想让新版本 publish 时同 family 旧 active 版本被原子置 superseded（事件带 replacement），以便版本演进不留双活旧版（合同 acceptance[1] 版本可追溯）。
19. 作为经验发布者，我想让被替代/撤回的旧版本快照与历史事件全保留，以便失效不删除只迁移（与铁律 3 同构）。
20. 作为下一事项的执行者，我想按项目 + 关键词召回可用记忆（applies 命中/excludes 排除 + 可解释排序〔命中得分与理由逐条可见〕+ 字符预算 Top-k〔超限进 excluded 明示〕+ conflict_key 冲突显式分组），以便拿到的是带引用、可解释、预算内的上下文包（蓝图「最小 RAG」：元数据过滤、可解释排序、Top-k）。
21. 作为下一事项的执行者，我想让撤回（revoked）或被替代（superseded）的记忆不进召回、跨项目记忆不进召回、同源事项不得独立复用，以便默认上下文不被失效或越界经验污染（合同 acceptance[2] 前半）。
22. 作为下一事项的执行者，我想让检索不到时召回包如实为空，以便「没有可复用经验」是诚实结论而不是编造召回。
23. 作为采用决策人，我想对召回包逐项做 adopt 决定（布尔 + 理由 + 操作人，零采用也落账），以便「决定即证据」。
24. 作为采用决策人，我想让采用决定把资产全文快照封进 BIND（plan/task 双唯一，一次交付最多一条），以便采用快照不可漂移（合同 acceptance[1] 采用快照可追溯）。
25. 作为复验执行者，我想按五相位落复验证据（precheck/implement/eval 逐相位 + review/outcome 收口；不收自报哈希——只给账本记录引用、模块自取现算），以便后续验证不依赖人的自觉（合同 acceptance[1] 后续验证可追溯）。
26. 作为具名复验验收人，我想让 outcome=passed 强制三相位齐全且全部 passed 且复核具名（缺则「复用验证缺少具名验收」），以便复用成功不能自封。
27. 作为审计者，我想让每次读取重算 sha256 复核（来源快照/召回包/采用快照），以便内容漂移报错而不静默（合同 acceptance[1] 状态可追溯的完整性面）。
28. 作为面板使用者，我想在任务视图里看到 evolution 块（total/verified/items）与列表第九计数 verified_evolutions，以便「这条反馈后来改进了吗、验证了吗」在面板可见（L14 因果交接兑现）。
29. 作为课程执行者，我想让本讲需求 Spec 冻结时强制关联本次新增 eval 用例（六段必填 ≤40000 + 验收段词边界显式关联 + 课程写集/验收/完成定义注入），以便动态 Eval 要求（合同 dynamic_eval_required=true 首见）有承载。
30. 作为课程执行者，我想让新增用例与静态合同重名时被拒、让起始证据核对「既有合同全绿 + 至少一个新增用例真实失败」，以便起始红是机器判定的形式化事实，不是口头承诺。
31. 作为 ERP 使用者，我想让 R1（采购审批入库两段事务窗口：status 写入与库存变更分两段，中断窗口部分提交违反五表不变量——L12 运行实证）作为真实反馈走完整治理链（FB 登记 → 具名审核 → evolution 立项 → 拷贝树原子化改进），以便「交付反馈驱动的 ERP 小改进」是本讲亲手走通的业务案例（erp_increment，D7 用户选定）。
32. 作为 ERP 使用者，我想让 R1 改进前后的证据 = 同一断言面（l15_receiving_interrupt_atomicity）在拷贝树改进前后两份报告（前红后绿）+ 客户自身 eval 前后照跑双绿，以便「升级有效 + 不破坏客户合同」都有原件（合同描述「保留升级前后证据」）。
33. 作为只读铁律守护者，我想让 R1 改进只发生在拷贝树、客户源码零改动（vendors 双 submodule status 恒空复核），以便客户真理不被复刻产物污染。
34. 作为验收人，我想让 L15Checks 默认门承载全部 L15 新面登记项（raw_feedback 四拍 + EVALS blocking 静态断言 + 演进/记忆链 + 动态起始证据 + 指纹），L13 复验面经 l13 DeliveryChecks 默认门并列照跑（断言面属主不变——L14 口径，mvn test 内承载 + 收口两门结论并列），以便合同面全数有机检对应物。
35. 作为验收人，我想让收口含冻结指纹复核（S01 冻结面〔经 tag 读取〕+ 上游 evolution.py/feedback.py/delivery_view.py evolution 段 + 客户面源件 + 本讲 Java 源件）与全量 `mvn test` 绿（含 golden 六重放 + L07–L14 合同零回归），以便旧能力零回归、对照面未被偷偷改动。

## Implementation Decisions

- **范围与对照源**（讲义 D1/D2）：主体对照 = S01 冻结面（ADR-0006 精神——冻结面是本仓建成件的对照基准；project 维度、七命令、HUMAN_FORBIDDEN 含 claude 增补全直承）+ 上游 `evolution.py` 全链断言面 + 上游现版 learning.py **仅取 evolution 连接缝**（source() 接 evolution_id + 失败轨迹门槛 + create() feedback_id 级联）；分歧落账：上游现版 initiative 维度重构不采纳（S01 project 维度是本仓合同）；词面逐句对齐（create/review/assets/verify 门词面、五分类、七资产类型、「复用验证缺少具名验收」等全部继承原文）。
- **落库**（讲义 D3）：单库直承（上游 feedback + evolutions + evolution_events + learning_* 五表 + tasks 同库；S01 D3 先例「不建第二套账本」）——L15 新运行库 `.runtime/course/L15-evolution/`，各 Store 构造逻辑自带建表（新库自然重建全表）；**L13 库（L13-delivery/）与 L14 库（L14-panel/）只读封存不动**；记忆链五相位与任务账四相位不混用（信用内核冻结不动——S01 D4 直承）；跨账互证经绑定 payload 外键 + 读时重算。
