## Problem Statement

工作台已经能自建（L01–L06）、护住提交（L07–L08）、修与调度（L09–L12）、对外交付（L13–L14）、沉淀经验（L15）——但它至今只在「作者的会话与电脑」上被证明过。接手者拿到仓库后：不知道系统在陌生环境能不能按文档从零启动；现场冒出一个基线里没有的小需求时，没有一条被证明过的「抽取→Spec→受控执行→Eval→人审→发布证据」链路可走；交付完成后，没有一份让没跟过过程的人能定位需求、Diff、Eval、人审与剩余风险的发布索引——「完成」的说法只能靠作者自述。

## Solution

建三件能力收口课程：①**发布证据索引**——对已完成任务一键汇集五要素证据引用（sha256 指纹 + 运行目录内相对路径 + 后缀白名单），如实列出全部缺项，状态恒「待人审」，永不代签；②**冷启动**——一条只读安装自检命令 + 干净克隆按文档命令链启动实验 + 记忆库副本迁移（经验可携带，检索不到如实为空）；③**现场抽取全链**——用户已具名抽定 P3 缺货登记（此前未实现经探针核验），走真实交付链在受控拷贝树实现（拒绝照旧、登记是留痕不是放行、不建负库存），新增动态用例先真实失败，三态证据（正常/失败/失败后不变）齐备，最后由发布索引对**真实任务**组装发布证据。

## User Stories

1. 作为接手者，我想对任意已完成任务一键汇集发布证据引用（spec / Diff 摘录 / 前后置 Eval 报告与 receipt / 可选冷启动、产品、剩余风险三件），以便没跟过过程的人也能定位全部证据。
2. 作为接手者，我想让每条引用带 sha256、字节数与运行目录内相对路径，以便文件真实性可独立复核而非信任作者自述。
3. 作为审计者，我想让人审缺席、执行者名义（agent: 前缀）或非 approve 决定都成为 human_acceptance 缺项，以便执行者自签在发布面上不可掩饰。
4. 作为审计者，我想让差分未接受、后置 Eval 未通过、Spec 冻结后被改动、报告与账面不一致、范围外改动各成独立缺项，以便「看似完整」与「真的完整」机器可分。
5. 作为审计者，我想让证据文件在运行目录之外或后缀白名单之外时被直接拒绝（词面「必须是本运行目录内的证据文件」），以便证据引用不越界、不指向任意路径。
6. 作为审计者，我想让空文件与缺席文件成为缺项而不是报错，以便索引如实列缺而不是中途崩溃。
7. 作为验收人，我想让发布索引状态恒为「待人审」并附三条 limitations（「本命令不批准任务、不发布版本，也不证明学生结业」），以便发布索引永远不构成代签（铁律 2 的发布面）。
8. 作为接手者，我想让 Diff 摘录随索引写盘，以便改动一眼可核对（截短局限已在 limitations 声明，不冒充完整 Patch）。
9. 作为审计者，我想让 Spec 冻结 sha 与现算 sha 对照并留 expected_sha256，以便冻结后任何变更必被发现。
10. 作为答辩观众，我想让剩余风险清单经 --risks-file 进入索引，以便「解释一项剩余风险」有正式落点而非口头。
11. 作为工具开发者，我想让索引输出 schema 稳定（workbench.release-index/v1）的 JSON 与命令行返回体，以便后续工具与答辩脚本可程序化消费。
12. 作为接手者，我想用 environment-check 一条命令只读检查安装六面（JDK / 编译产物 / 依赖清单落盘 / golden 基准 / 面板三件 / wb 包装脚本），以便接手第一步不靠猜。
13. 作为接手者，我想让安装检查只查不修（scope: installation），以便冷启动自检不会顺手改系统状态。
14. 作为接手者，我想在干净克隆里按文档命令链（全量测试 → 自检 → 起服务 → 面板可见）跑通系统，以便「离开作者的会话和电脑还能继续交付」得到实证而非假设。
15. 作为接手者，我想让冷启动服务用全新运行库（无作者残留数据），以便对作者会话状态的隐性依赖当场暴露。
16. 作为接手者，我想拿到既有记忆库的文件副本并在新环境检索到带引用的上下文包，以便经验可携带（迁移即复制，源库原件恒只读）。
17. 作为接手者，我想让零记忆库的检索如实为空，以便「检索不到」不被编造（记忆系统语义的冷启动实证）。
18. 作为验收人，我想让需求抽取时序机器可证（起始红 < 候选池 < 抽取 < Spec 冻结），以便「答辩现场抽取」不是事后补写（合同 acceptance[0]）。
19. 作为验收人，我想让候选池只备选不定选且假条目经探针排除（十四条在场面已剔除），以便「此前未实现」经同口径核验背书。
20. 作为验收人，我想让抽定后立即复验零命中并留前置事实（InsufficientStock 拒绝在场、登记面缺席），以便 P3 的「基线尚未实现」有正面证明。
21. 作为审计者，我想让 Claude 在抽定前对池内任何条目零预写，以便「预写即作弊」成为可查红线。
22. 作为销售员，我想让缺货时创建/预留照旧被拒（InsufficientStock 原语义与词面不动），以便库存边界（可用库存不能为负）不因新功能松动。
23. 作为销售员，我想在缺货被拒后登记未满足需求（商品 / 数量 / 登记日期 / 可选备注），以便真实需求不随一次拒绝口头流失。
24. 作为补货计划员，我想按商品与日期只读查询登记列表，以便补货决策有结构化依据。
25. 作为审计者，我想让登记不建负库存、不碰库存账，以便登记是拒绝的后件留痕而非变相放行（「先记账后修正」的反面）。
26. 作为审计者，我想让重复或无效登记被拒、且拒绝后登记面与库存面数据不变，以便「失败后不变状态」有独立证据（合同 acceptance[1] 第三态）。
27. 作为开发者，我想让登记面在受控拷贝树实现并经客户自身 eval 权威验证（升级前红 / 升级后绿 + 客户既有 eval 前后照跑双绿），以便 vendors 只读铁律下改进仍可交付。
28. 作为接手者，我想让 P3 现场需求走真实交付链（提交受理 → 执行 → 评测 → 停在人审 → 具名批准完成），以便发布索引组装的是真实任务而非夹具数据。
29. 作为开发者，我想让动态用例 l16_backorder_after_insufficient_stock 在实现前于拷贝树（vendors 原样）真实失败，以便「新增用例先真实失败」形式化落地（dynamicEvalRequired=true 真链路首用）。
30. 作为开发者，我想让动态用例经冻结关联六段 Spec（验收段词边界显式关联 + 与静态合同重名拒绝），以便现场需求的验收与既有合同互不混淆。
31. 作为审计者，我想让三态证据（正常绿 / 失败红 / 失败后不变）同入动态用例与证据账，以便合同 acceptance[1] 的三态各有新证据。

## Implementation Decisions

- **两 REGISTRY 命令**（接缝 1，上游 CLI 同形）：`release-index`（task_id 位置参数 + --runtime-dir + --cold-start-evidence/--product-evidence/--risks-file 三可选）与 `environment-check`（无必填参数）；错误走顶层 JSON 错误契约。
- **ReleaseIndex**（对照上游 release_index.py 逐段直承）：读 L16-transfer 运行库的 delivery TaskStore 公开面（接缝 3，不建新存储缝）；事件按四词面取证——`受控执行阶段完成` L13 已在场，`本次需求 Spec 已冻结` / `执行前课程 Eval 已完成` / `课程红绿差分判定已完成` 由 P3 现场交付链在对应相位补齐（真链集成点，非映射表）；引用边界（运行目录内 + 后缀白名单六类 + 非空）与全部缺项类目词面逐字直承；输出 `release-index/<task>/<uuid>/` 下 index.json + diff-excerpt.txt，命令行返回 {path, task_id, index_status, evidence_gaps}；index_status 恒 requires_human_review；limitations 三条词面原样。
- **EnvironmentCheck**（对照上游 environment_check.py）：六面检查（java / compiled_classes / dependency_classpath / golden_resources / web_panel_assets / wb_wrapper——红测试已合同化）只读；顶层 ok = all(checks)；默认 product_checked=false（客户探针不进本命令，见 Out of Scope）。
- **L16Checks 默认门**（接缝 2，七件登记项定形）：l16_release_index_assembly（组装与缺项全类目）/ l16_cold_start_checks（六面只读）/ l16_live_draw_sequence（时序核验：红证据 < 候选池 < 抽取 < 冻结）/ l16_three_state_evidence / l16_dynamic_start_evidence（既有合同绿 + 新用例真实红 + 独立验证三断言）/ l16_bound_eval_reverify（L13 门照跑承载）/ l16_frozen_fingerprints（按文件序）。
- **P3 缺货登记拷贝树交付**（接缝 4，L15 R1 同型）：新拷贝树（永不写回 vendors，双 submodule 恒空复核）；登记 = 独立登记表（商品 / 数量 / 登记日期 / 可选备注 / 可选来源引用）+ 登记入口（拒绝后件语义）+ 只读列表查询；拒绝链（InsufficientStock 三处守卫）零改动；升级前后证据 = 动态用例两份报告 + 客户既有 eval 前后照跑双绿。
- **动态用例** `l16_backorder_after_insufficient_stock`：断言与预期留 Java，经子进程 python 驱动拷贝树客户实现；DynamicSpecFreeze 冻结关联（六段 ≤40000 + 词边界 + 课程写集/具名人审注入 + 重名拒绝）+ startEvidence 起始红三态。
- **P3 真实交付链**：L16-transfer 运行库（同一库承载交付任务 + 迁移记忆副本——上游单库多账连通同形）；任务经 delivery 提交受理真实链走至具名批准完成；链上补齐三词面事件后由 release-index 对该真实任务组装。
- **冷启动实验**：本地路径 git clone 本仓到新目录 → 全量 mvn test → environment-check → delivery-serve 全新运行库起服务 → 面板可见（curl 原件）；记忆迁移 = L15 运行库文件副本入 L16-transfer（迁移即复制——「快照不随原文件变」同构，原件恒只读）→ learn-recall 带引用 + 新库空召回对照；实验原件落 16-transfer/ 子根。
- **结业面**：结业检查表入证据账（L01–L16 每讲一行指针，状态唯一事实源仍是 roadmap）；收官 tag 验收合并后用户具名打（Claude 不代打）。
