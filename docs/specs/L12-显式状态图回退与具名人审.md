## Problem Statement

L11 之后，我能把一项交付放进有停止条件的修复 Loop（L10）纵向重复，也能把互相独立的子任务安全并行（L11）。但交付还剩一类去向没有显式化：**检查通过后要等人**——目前人审只是任务账里的 `pending_human_review` 状态，没有「停在等待、具名批准后完成、打回后回退重查」的可执行控制面；**程序重启后要从可靠位置继续**——没有一份状态文件能回答「等的是哪版、依据哪份报告、谁批的、还能返工几轮」；**回退要有据**——打回后形成新候选必须重新检查，旧绿灯不能沿用，这条规则目前只存在于纪律里而不存在于代码里。上游参考件 `agent/graph.py` 给出了最小状态机（develop→test→rework/human_review→awaiting_human_review→completed + 具名审核 + 退出码 0/3/2），但它是 Python 教学支架（develop 未接真实执行器、姓名不认证身份、批准未绑定候选、move 未验边——四个局限上游明示如实暴露），且无 Java 对应物。同时，本讲的业务增量（审批后入库）在客户侧守卫与幂等正确，但 **R1–R6 键治理缺口**（L11 乙子代理移交：两段事务窗口、换键双入、None 键绕过、已消费键静默吞、双事件误拒、authority 事务外）没有任何运行实证裁判；「Graph 状态与 ERP 权威状态可对账」（合同 acceptance[2]）也没有一次真实走通的证据链。

## Solution

工作台新增**Graph 控制器 Java 对应物**（`workbench/graph/` 新子包 + REGISTRY `graph-run`——agent 家族第四件，上游 `agent/` 四件收齐：六状态机 develop/test/rework/human_review/awaiting_human_review→completed/stopped/failed，逐句对齐上游：等待退出码 3、打回回退重查、终态重读不重执行、异常显式 failed、`--suite-command` 子进程缝承载检查注入、rework 节点复用 RepairMapper、状态文件与上游 `_result` 十字段同形）。配套建设审批入库面探针与统一入口（`ApprovalProbe` 九模式驱动客户 `approve_purchase`/`reject_purchase`/`receive_purchase` 真身——临时库 + 触发器注入内联（上游逐字源）+ 五表/阶段快照，断言留 Java；`ApprovalChecks` 十件默认门全 blocking + 两必红选跑）。故障与恢复以**预期红留证**钉进证据链：`l12_status_write_failure`（断言理想不变量前后快照相等——客户部分提交违反之，R1 运行实证）/ `l12_key_collision`（断言 received ⇒ +7 流水——客户已消费键静默吞违反之，R4 运行实证）/ `l12_approval_recovery_same_key`（触发器移除后原键重试补齐单据不重复加库存——绿，且「恢复成功不证明第一次操作原子性成立」）。acceptance[2] 由**受控对账实验**承载：graph 端以真实统一入口命令为 suite 走通「等待 rc 3 → 具名批准 rc 0」，业务端五表阶段快照，双端原件 + 对账表落采集根。R1–R6 对照账三分类（运行实证/引用不复现/待验证），客户原样行为永不写成复刻缺陷（上游明示本次未修复产品代码）；教学 reviewer 字符串不冒充身份认证；stale-approval / unchecked-move / empty-report 上游缺口如实暴露不粉饰（治理层留后续讲次）。

## User Stories

1. 作为具名验收人，我想要一个显式状态图控制器（`graph-run`），以便「检查通过后等人、打回后回退、重启后从可靠位置继续」由可执行规则承载而不是散落在流程纪律里。
2. 作为具名验收人，我想要检查通过后停在等待具名审核（退出码 3）且再次运行保持等待、不重新检查，以便等待是正确结果而不是失败、重复或自动接受。
3. 作为具名验收人，我想要打回后回退到修改、形成新候选后必须重新检查再重新等待，以便旧候选的绿灯与批准永不沿用给新候选。
4. 作为具名验收人，我想要等待点的批准绑定具名审核人（姓名 + 决定 + 时间落状态文件），以便人审记录不是一句含糊的「已批准」。
5. 作为具名验收人，我想要新运行直接传入批准不会被采纳（不在等待点则决定被忽略），以便批准只能针对真实的等待状态。
6. 作为具名验收人，我想要轮数上限到限时停止并保留剩余失败（不再宣称成功），以便流程不能为抵达「完成」绕开上限。
7. 作为具名验收人，我想要检查异常显式进入失败态并留 error（不静默吞），以便失败可接续、可追溯（铁律 3）。
8. 作为具名验收人，我想要完成/停止/失败等终态重读不重新执行（结果逐字不变、零新检查），以便重启幂等、旧证据不被覆盖。
9. 作为具名验收人，我想要未审批/已拒绝采购入库被阻断（ApprovalRequired）且前后五表不变（合同 acceptance[0]），以便「未经具名审批不得改变库存」有拒绝面实证而不只是守卫代码在场。
10. 作为具名验收人，我想要具名审批后一次幂等入库（received + 17/2/15 + 恰一条 +7 流水 + `approved_by` 具名 + OTHER/PR-OTHER 保留），以便合同 acceptance[1] 的业务事实链完整可对账。
11. 作为具名验收人，我想要同键重放五表不变（`idempotent_replay`）与已入库后换键被拒（InvalidTransition），以便幂等键的两面（重放安全 / 换键必拒）都有裁判。
12. 作为具名验收人，我想要审批人空白被拒绝（ValueError）且五表不变，以便「具名」不是可选装饰。
13. 作为具名验收人，我想要 Graph 状态与 ERP 权威状态可对账（合同 acceptance[2]）——双端身份并列对账表（trace/report_summary/reviewer/reviewed_at × PR-TARGET received/approved_by/event_key/17/2/15/+7 流水），以便软件交付面与业务执行面的证据链互相印证、可交接。
14. 作为具名验收人，我想要对账实验里 graph 的 test 节点跑真实业务检查（统一入口命令做 suite），以便「ERP 权威状态」面对应真实检查而不是合成替身。
15. 作为具名验收人，我想要部分提交故障（教学触发器阻断状态翻转）如实暴露——库存已 +7、单据仍 approved、原子性断言预期红留证，以便 R1 两段事务窗口有运行实证且不被粉饰成「已原子」。
16. 作为具名验收人，我想要已消费键静默吞故障如实暴露——单据 received 但库存仍 10、无 +7 流水、对账断言预期红留证，以便 R4「失败显示成成功」有实证（业务边界 5 活教材）。
17. 作为具名验收人，我想要同键恢复成功（补齐单据、不重复加库存）的同时明确「恢复成功不证明第一次操作原子性成立」，以便恢复语义不被夸大。
18. 作为具名验收人，我想要 R1–R6 对照账三分类（R1/R4 运行实证；R2/R3/R5 引用 L11 乙发现不复现；R6 保留待验证），以便每条风险有出处、口径与上游一致（客户原样行为不写成复刻缺陷）。
19. 作为具名验收人，我想要客户绑定 eval 两件以客户原名照跑（`purchase_requires_approval` + `receiving_is_idempotent`），以便本仓库绿灯不冒充客户业务结论（ADR-0005）。
20. 作为具名验收人，我想要 `receiving_is_idempotent` 的实际断言面（`receive_stock` 键维度）与单据维度防重的差距如实入账，以便「eval 绿 ≠ 键治理完备」被具体指出而不是一句空话。
21. 作为具名验收人，我想要空报告零阻断也进等待的接口反例如实暴露（不粉饰），以便消费者校验缺口是学习材料而不是被顺手「修好」。
22. 作为具名验收人，我想要教学 reviewer 字符串不认证身份、stale-approval 批准未绑定候选、unchecked-move 直调跳步三个上游局限如实暴露，以便最小支架的边界明示（治理层留后续讲次，两层不混称）。
23. 作为执行者（Claude），我想要 `--suite-command` 子进程缝注入检查命令（stdout = schema 1.0 报告、rc 0 绿 / 1 红），以便控制模式的合成输入与对账实验的真实检查走同一条缝（L10 LoopRunner 先例）。
24. 作为执行者，我想要 rework 节点复用 RepairMapper 生成修复任务（落状态文件同目录，可参数覆盖），以便修复映射不重复建设（L09 件复用，L10 loop 同款先例）。
25. 作为执行者，我想要状态文件与上游 `_result` 十字段同形（status/rounds/trace/report_summary/report/repair_task/error/reviewer/review_decision/reviewed_at），以便与上游对照面不断裂、接手者按字段倒推要保存什么。
26. 作为执行者，我想要探针以子进程 python 驱动客户审批/入库面（临时库、五表 + 阶段快照、回报原始观察不判对错、断言留 Java、三量走 `product()` 计算列），以便客户真身不被进程内 import 污染（L05+ 结构翻译点承袭、L10 教训④ 承袭）。
27. 作为执行者，我想要触发器注入内联在探针模式里（上游 `purchase_approval_lab.py:66-67` 逐字源）、不新建注入装置件、不建常驻拷贝树，以便注入形态与上游一致（运行时数据库注入非源码改动，与 L09–L11 差异如实记录）。
28. 作为执行者，我想要两必红项经 `--case` 选跑而不进默认门，以便「检查发现客户原样缺陷」是护栏不是把门卡死的污染（L11 premature-stock / L09 leak / L10 refuse-all 先例）。
29. 作为复验者，我想要十六控制模式全数机检并对照上游表逐项断言（状态名 / 检查调用数 / 轮数 / 新增检查数），以便控制器每个分支有合同证据。
30. 作为复验者，我想要 malformed-state / save-error 走顶层异常边界（JSON 错误契约 rc 1，词面含异常类型），以便状态 IO 故障不吞不伪装（退出码面与上游裸栈一致，输出形态按本仓 L01 合同）。
31. 作为复验者，我想要客户 eval 双树与 `flowerp/service.py` 指纹复核进默认门、本讲 Java 源件指纹初冻与收口复核走证据账层面，以便检查冻结不被偷偷改动（L10/L11 承载面先例直承）。
32. 作为复验者，我想要失败报告留史不删（两必红项报告与恢复前状态永久在案、状态文件新路径不覆盖旧证据），以便铁律 3 落实（上游 `open("x")` 同语义）。
33. 作为接手者（重启恢复视角），我想要状态文件告诉我等哪版、依据哪份报告摘要、谁批的、异常是什么、还能返工几轮，以便重启后不需要考古聊天记录。
34. 作为采购审批负责人（业务视角），我想要我的批准只授权我批准的那张单（PR-TARGET），以便别的单（PR-OTHER）或软件候选的绿灯不能借用我的授权。
35. 作为既有申请与订单（PR-OTHER / OTHER，业务视角），我想要 PR-TARGET 审批与入库前后我的记录与预占不变，以便别人的流程不触碰我的意图（2 恒在，17/2/15 成立）。

## Implementation Decisions

- **graph 落点与 CLI 形态**（讲义 D1）：新子包 `workbench/graph/`（`repair/`/`loop/`/`schedule/` 先例——agent 家族第四件收齐）+ **REGISTRY `graph-run`**（上游 `agent/graph.py` 有 main——argparse 六参 `--max-rounds/--reject-once/--require-human-review/--state-file/--review-decision/--reviewer`；退出码 0 completed / 3 awaiting_human_review / 2 其余）；参数校验走 UsageException rc 2（L10 LoopRunner 口径承袭——上游 ValueError 裸抛 rc 1 的形态差异如实入账）。
- **状态机语义逐句对齐上游**：六工作状态 develop/test/rework/human_review/awaiting_human_review + 终态 completed/stopped/failed；`move` 只记转移**不验边**（unchecked-move 反例如实暴露）；develop 推进轮数、超限停止；test 跑 suite、阻断失败 → rework + 修复任务、零阻断 → human_review；rework 未到限回 develop；human_review：reject_once 演示打回 → develop，`require_human_review or persistence` → awaiting，否则本地演示策略自动 completed；等待点决定处理在主循环前（approve → completed / reject → develop，具名 reviewer/review_decision/reviewed_at 落状态；决定缺审核人拒绝）；异常显式 failed 留 error；`_load_state` 容错键名（status/state、rounds/round_no）。
- **接缝**（讲义 D2）：`--suite-command` 子进程缝（Shlex 拆分、stdout = schema 1.0 报告、rc 0 绿 / 1 红——LoopRunner 同款）+ 修复任务复用 RepairMapper（落 state-file 同目录 `graph-repair-task.json`，`--repair-task-path` 可覆盖）+ 状态文件 JSON 与上游 `_result` 十字段同形（运行目录 `.runtime/course/L12-graph/`）。
- **探针与登记项**（讲义 D4）：`workbench.evals.l12.ApprovalProbe` 九模式（approved/unapproved/blank-reviewer/rejected/replay/different-key/status-write-failure/recovery-same-key/key-collision；夹具逐字段对齐上游 lab：A 商品 + `receive_stock 10 "opening"` + OTHER×2 预占 + PR-OTHER A×3 + PR-TARGET A×7；五表 + 阶段快照 before_approval/before_receive/after_*/final）；`ApprovalChecks` 独立 main 挂 EvalHarness：默认门十件全 blocking——七业务拍（`l12_approval_approved`/`_unapproved`/`_rejected`/`_blank_reviewer`/`_replay`/`_different_key`/`_recovery_same_key`）+ 客户 `purchase_requires_approval`、`receiving_is_idempotent` 原名照跑（子进程 python，L09/L10/L11 同族）+ `l12_frozen_checks`（客户 eval 双树 + `flowerp/service.py`）；**两必红选跑不进默认门**：`l12_status_write_failure`（断言理想不变量前后快照相等——R1 部分提交违反，预期红）/ `l12_key_collision`（断言 received ⇒ +7 流水——R4 静默吞违反，预期红）——性质注明客户原样行为非注入缺陷。
- **触发器注入内联**：上游 `purchase_approval_lab.py:66-67` 逐字源（BEFORE UPDATE OF status 触发器 RAISE ABORT + DROP TRIGGER 恢复），内联在探针模式里；**不建常驻拷贝树**（临时库随起随灭，永不触 vendors——铁律 1；与 L09–L11 差异如实记录）。
- **受控对账实验**（讲义 D6）：graph 端真实走通——`graph-run --suite-command "<ApprovalChecks 绝对路径命令>" --require-human-review --state-file lesson-12-submission/12-reconciliation/state.json` → 等待 rc 3（原件封存）→ `--review-decision approve --reviewer "TEACHING reviewer"`（教学替身如实标注；真实具名验收 = 用户按讲义 §4 恒例）→ rc 0；业务端 approved 拍阶段快照；对账表双端身份并列落同目录。
- **命名**：分支 `lesson-12`；证据账 `docs/replication/evidence/L12.md`；任务 `CASE-WB-L12-001` @ `.runtime/course/L01-workbench-java/`；采集根 `lesson-12-submission/`（含 `12-reconciliation/` 子根）。
- **CI**：本讲不动 L08 工作流（CI_GATE_SPEC 合同写集映射件；ApprovalChecks 远程复验缺口如实声明，本地全量门承载——D8）。

## Testing Decisions

- **好测试只测外部行为**：经公开接缝断言可观察输出（退出码、stdout JSON、状态文件内容、登记项报告、落盘快照与对账件），不直调私有方法；探针回报原始观察，预期值 Java 侧独立计算不抄返回值（三量走 `product()` 计算列）。
- **起始红三面**：`graph-run` 未注册（rc 2 invalid choice）/ `ApprovalChecks` main 缺席 / 探针缺席，经 testsupport/Cli 真实子进程断言（Java 编译不绑实现类，L06-java 教训承袭）。
- **十六模式机检**：表驱动对照上游 README 表逐项（状态名 / 检查调用数 / 轮数 / 新增检查数——resume/approve/stale-approval/reject-at-limit/terminal-rerun 断言零新增检查，reject 断言一次重查）；合成输入经 `--suite-command` 注入脚本（L10「CLI 参数即注入缝」先例——上游 unittest.mock patch 的本仓对应面）；malformed-state / save-error 走顶层边界 rc 1。
- **九模式合同测试**：探针各模式的夹具、快照与断言构成（含两必红项的「断言理想不变量、客户违反即红」语义）。
- **先例**：L09/L10/L11 Checks+Probe 合同测试（业务面收口形态与 `--case` 选跑）、L07+ 冻结指纹复核、RepairMapper/EvalHarness 复用面；golden 六重放不涉本讲（无 Python 先例，验收门替代 = 合同测试 + 默认门/必红留证 + 对账链 + 对照账 + 指纹 + 全量 mvn test，讲义 D9）。
