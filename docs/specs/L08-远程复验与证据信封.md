## Problem Statement

L07 之后，统一 Harness 与 Stop 护栏只在我自己的电脑上、在我自己的会话里运行。具名验收人面对一份候选分支时无法回答：这份绿报告是不是真的出自那一份代码、那一组检查？如果远程流程少跑一项、取错版本、或者吞掉失败退出码，绿色仍然没有意义——而验收人目前没有任何可追查的独立运行证据可以下钻核对。同时，本讲的业务交付（销售订单整单原子预占）虽然客户实现已在场且正确，但"任一行缺货时整单失败且无部分预占"这条规则至今只有单行缺货的检查覆盖，中途写入失败能否整体回滚从未被检验过。

## Solution

把同一套 Eval 接入 CI：候选分支上建立 GitHub Actions 工作流，让它取明确版本（submodule 固定指针）、准备与本地同形的环境、调用与本地完全相同的统一入口（同一命令、同一组登记项、同一报告 schema），再把报告与一封"证据信封"（绑定运行身份与报告哈希）作为 artifact 归档。用同一工作流的三个受控状态完成 A 假绿 → B 可信红 → C 可信绿的对照：证明检查流程能诚实暴露失败（B），业务在同一标准下恢复正确（C），而吞掉失败的绿色不可信（A）。业务面的原子性区分器（write-error 中途故障模式）由教学注入装置在拷贝树上构造——客户实现不动，永不写回 vendors。

## User Stories

1. 作为具名验收人，我想要候选分支的每次 CI 运行都留下可下载的原始报告与信封，以便我不依赖任何人的转述就能核对这次运行检查了什么、结论是什么。
2. 作为具名验收人，我想要 B 与 C 两次运行的报告解压后能重算 SHA-256 并与信封内的哈希对上，以便确认收到的文件就是当时生成的那份。
3. 作为具名验收人，我想要 A/B/C 三个工作流状态的 diff 各只动一个层，以便确认红色确实来自失败传播修复、绿色确实来自业务恢复，而不是混装改动。
4. 作为具名验收人，我想要 A 态（吞失败）的工作流永不进入 master，以便生产门上不存在任何会假装通过的路径。
5. 作为具名验收人，我想要 CI 运行记录（Run ID、attempt、checkout SHA、Job 结论）与下载原件一起入证据账，以便从平台入口到报告字节全程可下钻。
6. 作为执行者（Claude），我想要一个注入装置在拷贝树上复刻上游权威形态的教学缺陷（一行提前提交），以便在客户实现正确的前提下构造"业务缺陷在场"的可控对照，且不伪称客户事故。
7. 作为执行者，我想要注入装置带锚点唯一性校验，以便注入位置可机检、diff 可逐字对上游，恢复动作就是同一棵树上的一行还原。
8. 作为执行者，我想要统一入口以独立 main 形态收口八件登记项（三件原子预占模式探针 + 两件客户绑定 eval 原样名照跑 + 信封诚实六边界 + L07 回归 + 冻结指纹复核），以便本地、CI 与显式复验调用的是同一个裁判。
9. 作为执行者，我想要探针只回报原始观察（四表前后快照、状态、余额、错误）而断言全部留在 Java 侧独立计算，以便检查与实现不共用同一套公式。
10. 作为执行者，我想要 write-error 模式用临时数据库上的标注触发器让第二条预占记录插入失败，以便检验写入开始后的回滚，而不是只检验写入前的拒绝。
11. 作为 CI 运行环境，我想要工作流先跑全量测试门再跑统一入口，以便环境准备失败或既有能力回归时不会产生误导性的业务报告。
12. 作为 CI 运行环境，我想要报告落在按 Run ID 与 attempt 隔离的非隐藏目录、上传步骤缺文件即报错，以便旧输出永不冒充本次证据。
13. 作为复验者，我想要信封消费者在缺报告、缺运行身份、畸形 JSON 时拒绝并返回非零退出码，以便这些材料在源头就被判为不合格而不是被包装成证据。
14. 作为复验者，我想要空报告的信封如实记录决策为空、被篡改的报告哈希失配可检、旧输出在命令失败时原样保留，以便信封作为关联证据的边界诚实可见。
15. 作为其他订单（业务视角），我想要任一行缺货时整单预占全部不生效，以便我的可用库存不会被别人失败的操作悄悄占住。
16. 作为其他订单，我想要正常路径（库存充足）被独立验证为整单预占成功，以便"拒绝所有订单"这种伪修复无法蒙混过关。
17. 作为正式销售流程，我想要预占失败后订单保持 confirmed（先确认再预占的入口合同），以便检查不会误套另一个入口的状态语义要求退回草稿。
18. 作为用户，我想要本地链（同命令红绿：缺陷树红 → 一行恢复 → 绿）与 CI 链（三 Run）在证据账中分列，以便两类证据不互相冒充。
19. 作为用户，我想要 SIMULATED 身份只出现在本地机制实验并如实标注，以便任何本地模拟永不冒充远程运行。
20. 作为用户，我想要 L08 收口时执行上游检查点裁定（fetch 现查 L09–L16 上架面），以便后半程是逐讲还是按阶段由我具名裁决而不是默认滑过去。

## Implementation Decisions

- **CI 承载**：GitHub Actions（origin 即 GitHub）；工作流触发覆盖候选分支 push 与 PR；checkout 带 submodule 递归；Java 21 + Python 3.12 + 本地同形 venv（客户纯标准库，零装包）；全量测试门先行（顺带落 classpath 清单供 CLI 包装用）；报告目录按 run_id-attempt 隔离且非隐藏；上传步骤 `if: always()` 且缺文件即 error。
- **统一入口**：独立 main（不进命令注册表，l05/l06/l07 先例），argv 面（`--target` 必填客户树根、`--python` 缺省本地 venv 解释器、`--report-path`/`--no-report`）与 L07 收口件同形；报告经统一 Harness（schema 1.0、独占写、退出码由 blocking 失败决定）——与客户及 L06/L07 同一 Eval 身份。
- **登记项构成（全 blocking，八件）**：原子预占三模式（pass / shortage / write-error）+ 客户绑定 eval 两件以客户原名照跑（子进程驱动客户 harness，业务权威）+ 信封诚实六边界机检（合同名原样）+ L07 口径进程内复用（旧能力在场，旧检查照跑不删弱）+ 客户 eval 双树指纹复核。缺陷树下的预期唯一红点 = write-error 模式（短缺在规划期即拒绝，正确树与缺陷树同样无残留——普通缺货不足以证明原子性，如实作为教学点）。
- **探针纪律**：子进程 python 驱动目标树客户实现，临时数据库自建，write-error 模式装标注触发器；回报原始观察 JSON 不判对错，独立预期与四表逐表对照断言全留 Java 侧；解释器路径显式传绝对值（解析器不做 PATH 查找）。
- **信封件**：进命令注册表（`ci-evidence`，L07 quality-gate 先例：合同工作台增量即工作台能力）；八字段对齐上游（commit/run/工作流/运行系统/运行时版本/suite/报告 SHA-256/报告决策），运行时版本字段按载体如实记 Java（不硬造上游的解释器字段名）；错误语义：缺报告或缺身份 → 非零 + stderr；成功才写输出文件，失败不动旧文件（旧输出残留边界因此可检）。
- **注入装置**：独立 main，拷贝目标树后按上游 diff 逐字插入一行提前提交（自带教学标注注释），锚点行唯一性校验；CI 与本地使用同一装置（不另写内联脚本，防两套口径漂移）。
- **A/B/C 三态承载**：候选分支上同一工作流文件三个 commit 状态——A（注入步骤在场 + 统一入口步骤字面 `continue-on-error` 吞失败）→ B（只删该行）→ C（只移注入、目标指回干净 submodule 树）；合并面 = C 态终态（吞失败与注入永不入 master，A/B 态在分支历史可回查）；"业务缺陷在场/不在场"由注入装置表达，形态差异（客户实现本就正确，注入是教学装置非真实事故）如实记录。
- **远程证据入账**：三 Run 各留平台元数据（采集自 CLI）+ 下载的报告与信封（解压后重算 SHA-256 对账）入采集根子目录（采集根永不移动）；另做一次"报告未生成"隔离运行留平台日志，证明缺报告时报错而非旧 artifact 补位。
- **CI 门规格文件**：仓库根新增 CI 门规格文档（门定义、受控对照规则、信封核对清单、合同通过标准四条），与工作流同入合同写集映射位。
- **命名**：候选分支 `lesson-08`；证据账、任务号、采集根均 L07 直承（无 -java 后缀——重走线已完结）。
- **收口附带动作**：L08 收口即执行上游检查点裁定（roadmap 阶段 4 行尾款）。

## Testing Decisions

- **好测试的定义**：只测公开接口的外部行为（退出码、stdout/stderr 词面、落盘文件内容与位置），不测内部函数；纯文本与合同 fixture 类直接读文件；真实业务红绿与真实 CI 运行不入 mvn 面，属候选期证据账（测试面不冒充真实运行）。
- **接缝（已具名确认，零新缝）**：
  - **CLI 子进程缝**（既有 testsupport 经真实 CLI 子进程驱动，L06/L07 同法，无编译绑定）：`ci-evidence` 命令合同（注册面、参数面、六边界非零与 stderr 词面、成功才写输出）+ 统一入口与注入装置的 argv 合同（缺 `--target` 非零、目标无客户包拒绝词面、锚点唯一性校验）。
  - **文本直读缝**（L07 待审投影完整性测试同法）：工作流终态静态断言（submodule 递归、全量门、统一入口、信封步骤、上传缺文件即 error、**终态无 continue-on-error**）+ CI 门规格文档在场。
- **起始红三面**（commit 1）：命令未注册（invalid choice 退出码）/ 统一入口 main 缺席（class not found）/ 工作流文件与门规格缺失（文本面）。
- **测试先例**：L07 本地护栏合同测试（替身承载协议面 + 真实事件链留给候选期）、L06 统一运行器合同测试（报告 schema 与退出码一致性）、golden 六重放（既有能力回归门，本讲继续照跑）。

## Out of Scope

- 不修改客户实现（vendors 只读；业务缺陷只发生在拷贝树，教学注入不伪称客户事故）。
- 不在本讲建 `course-status` 等上游待建设命令（如实标注待建设，不写成已建成）。
- 不把 CI 通过做成合并授权（具名验收与合并仍走候选分支机制 + 人工 `merge --no-ff`；PR 不经平台合并按钮）。
- 不复刻上游 `ci_signal_lab` / `envelope_boundary_lab` / `atomic_reservation_lab` 三个实验脚本的独立可运行形态（其教学语义分别内化为：六边界机检登记项、探针三模式；本地机制实验脚本不作为交付物）。
- 不做合并必需检查（branch protection）配置——上游明示"单有红灯不能证明平台已启用合并限制"，此项属平台治理动作，留用户另行决策。
- 后半程逐讲 or 按阶段的路线决策不在本 spec 内预判（L08 检查点裁定时由用户裁决）。

## Further Notes

- 信封的定位（上游口径逐字承接）：它是关联证据的一层，不是业务裁判，也不是合并授权——来源、内容完整、业务正确、人工接受是四种判断，后面的判断需要前面的依据，却不能互相替代。
- 上游已知的上传陷阱（artifact 上传默认排除隐藏目录文件）按非隐藏报告目录规避；上传成功不等于业务通过。
- 客户绑定 eval 的单行缺货覆盖面对提前提交注入不可见（规划期即拒绝）——这是"本讲新增多行与中途故障裁判"的直接依据，不是客户缺陷。
- 执行期到点配合点：动笔实现前用户显式 `/mattpocock-skills:implement`；起始红采集前 to-spec 已完成（本文件）；收口前 code-review 双轴复查候选分支。
