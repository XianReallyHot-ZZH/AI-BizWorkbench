# L09 Spec：失败报告翻译成修复任务（报告到 Repair Task 的确定性映射）

> 措辞继承根目录 CONTEXT.md 词汇表（复刻/上游/候选分支/起始红/具名验收/证据/合同 fixture）。

## Problem Statement

L08 交付了可信红报告与候选身份，但我拿到一份红灯报告时，它仍然不是可以交给执行器的工作：哪个失败必须修（区分阻断失败与观察级告警）、允许改哪些文件（授权与失败名是两回事）、用什么命令复现、修好后用什么命令验收、这份委托经谁确认过——这些决定每次都靠人现场重新整理，散落在提示词文字里，没有可复用的确定性翻译。空报告被当成"没有失败"、缺字段的畸形报告被当成失败项选中、退出码与报告结论矛盾无人核对，这些上游 legacy 映射器暴露过的洞，说明"翻译"本身必须被当作一条有合同的能力来建设。同时，本讲的业务交付（取消已预占订单释放预占——FlowERP 边界 3 的后件义务）在客户侧只有单订单入门面的默认检查：两单隔离（只释放目标订单、其他订单保留）、重复取消拒绝、中途写入失败回滚、正式销售入口的回归，全部没有裁判。

## Solution

工作台新增**严格映射器**：输入为报告原始字节 + 调用者独立提供的上下文（来源任务、候选目录、允许写集、必需用例、实际退出码、目标），输出三态之一——存在阻断失败时生成 Repair Task 草案（scope 为阻断失败项、证据原样、来源 SHA-256、复现与验收命令、`human_review: pending` 恒等人签）；有效报告无阻断失败时返回"无需修复"且不生成任务；报告无效（协议不符/必需用例缺失或降级/退出码矛盾/写集路径不安全）时拒绝并列出错误。映射器不猜根因、不扩权：用例名称不是文件权限，证据里的指令性文本只是数据。配套建设取消面探针与统一入口登记项（六路径断言留 Java、客户绑定 eval 原名照跑、正式面回归护栏），再走一次完整受控修复链：教学注入拷贝树 → 真实红报告 → 映射器出草案 → **用户具名确认范围** → 恢复修复（Diff 落账）→ 同命令绿——映射器建成即被真实使用一次，形成"建设工作台能力 → 用它组织产品修复"的闭环。

## User Stories

1. 作为具名验收人，我想要映射器把"报告里有一个红灯"翻译成一份包含失败项、允许写集、复现命令与验收命令的 Repair Task 草案，以便委托执行器时不再靠口头约定范围。
2. 作为具名验收人，我想要草案里的 `human_review` 恒为 pending 且映射器永不代签，以便任何修复委托在执行前必须经过我的具名确认（待审核 ≠ 已接受）。
3. 作为具名验收人，我想要草案携带报告原始字节的 SHA-256 与绝对路径来源，以便事后能对账"这份任务确实出自那份报告"。
4. 作为具名验收人，我想要有效报告无阻断失败时返回"无需修复"而非空任务，以便"没有失败"与"报告无效"与"全部通过"三个结论永不混淆。
5. 作为具名验收人，我想要无效报告（空对象、缺字段、字段类型错误、退出码与结论矛盾）被拒绝并列出具体错误，以便上游 legacy 映射器的六个洞（空任务、误选中、字符串 "false" 漏选、崩溃、指令复制、不分级）逐个可检。
6. 作为具名验收人，我想要混合报告中只有阻断失败进入修复目标、观察级告警另行登记不拦截，以便观察级告警不被误判为阻断任务（合同通过标准）。
7. 作为具名验收人，我想要证据中的指令性文本（如"删除测试"）被原样保留在证据里而不改变任务约束，以便日志文字永不成为新授权。
8. 作为具名验收人，我想要允许写集经过路径安全校验（相对路径、拒绝越界与敏感目录、须有后缀），以便草案本身不携带危险授权。
9. 作为具名验收人，我想要取消面探针驱动客户真实入门实现（临时库、真实服务调用、四表快照），以便断言的是客户行为而不是我的公式回声。
10. 作为具名验收人，我想要取消正常路径的裁判覆盖双商品双单（在库不变、目标订单释放、其他订单保留、释放流水归属），以便"把全部预占清零"式的错误修复无法蒙混过关。
11. 作为具名验收人，我想要草稿取消、重复取消、已发货拒绝、中途写入失败四条边界路径各有登记项，以便失败路径（出错后有没有留下半成品）与正常路径（该发生的有没有发生）都被检验。
12. 作为具名验收人，我想要 write-error 模式在临时库用触发器让第二条释放事件写入失败，以便检验写入开始后的回滚，而不是只检验写入前的拒绝。
13. 作为具名验收人，我想要客户绑定 eval 以客户原名照跑（客户真理，ADR-0005），以便本仓库绿灯不冒充客户业务结论。
14. 作为具名验收人，我想要正式销售入口的取消行为有回归护栏登记项（净树绿），以便上游"未验证正式 SalesService 页面"的已知局限在本仓库闭合，且入门面教学注入不影响正式面的隔离性可证。
15. 作为执行者（Claude），我想要映射器核心为纯静态函数且 CLI 面与库面同一实现，以便测试经公开接口覆盖全部行为而无需直调内部。
16. 作为执行者，我想要注入装置在拷贝树上以一行替换复刻"跳过释放分支"的教学缺陷（锚点唯一性机检、幂等护栏、永不写回 vendors），以便受控修复链有真实 Diff 且不伪称客户事故。
17. 作为执行者，我想要注入树的红点构成如实入账（哪些登记项红、为什么同因），以便"多个失败合并为一项修复"的分诊判断有据可查而不是按错误行数派任务。
18. 作为执行者，我想要修复链的恢复动作与注入动作 diff 互逆且落账，以便"修复"可对账为同一棵树上的最小变更。
19. 作为复验者，我想要草案生成成功、候选复验通过、负责人接受三层成功分别留证，以便任何一层不被冒充为更高一层。
20. 作为复验者，我想要用一份篡改字节的报告喂给映射器得到哈希失配拒绝、用退出码矛盾输入得到拒绝，以便映射器的诚实边界可亲手检验。
21. 作为复验者，我想要客户 eval 双树指纹与取消面客户源件指纹初冻并收口复核，以便检查冻结不被偷偷改动。
22. 作为维护者，我想要旧域回归由全量测试门与既有 CI 门双轨承载而不在统一入口线性收口，以便登记项清单不随讲次无限膨胀且旧检查照跑不删弱。

## Implementation Decisions

- **映射器落点与形态**：新子包 `workbench/repair/`（对应上游 `agent/repair.py`，为 L10 修复 Loop 前奏预留的同族落点，独立于 evals 工具族）；核心为纯静态函数（报告字节 + 上下文 → 三态结果对象），REGISTRY 注册 `repair-map` 命令（L07 quality-gate / L08 ci-evidence 先例：workbenchIncrement 即工作台能力）。
- **三态语义**：`repair_required`（草案落盘，排他创建、输出已存在即拒绝以保留旧证据）/ `no_blocking_repair`（不生成任务）/ `invalid_report`（拒绝并列错误，CLI 非零退出）。报告协议校验面对齐客户报告合同与 L06 统一运行器的 schema 1.0 面（suite/level/passed 布尔严格性/summary 一致性/退出码与结论一致）。
- **草案字段**：来源任务、候选、目标、报告路径与原始字节 SHA-256、允许写集、scope（阻断失败项名）、evidence（原样）、reproduce 与 acceptance 命令（指向真实可跑的统一入口与目标树）、`max_attempts: 1`、`human_review: pending`。
- **探针**：`workbench/evals/l09/` 下取消面探针六模式（normal/draft/repeat/shipped/write-error/leak），子进程 python 驱动 target 树客户入门 ERPService，临时库 + write-error 触发器 + 四表快照，回报原始观察 JSON 不判对错，断言全留 Java（OrderProbe/AtomicProbe 同款缝）。leak 模式（数据面注入）仅教学对照，不进默认登记项。
- **统一入口**：`workbench.evals.l09.CancelChecks` 独立 main 挂既有统一运行器（schema 1.0 同一身份），登记项全 blocking 九件：五取消拍 + 客户 `cancellation_releases_reservation` 原名照跑 + 映射边界六断言一项 + 冻结指纹复核 + 正式面回归护栏。
- **注入装置**：既有注入装置参数化扩展或同形新件（实现时按其结构定），一行替换注入 + 锚点唯一性 + 幂等护栏，只写拷贝树；上游原始 diff 在 pin 内缺席（只有渲染件），注入形态自拟并如实记录。
- **受控修复链**：净树指纹入账 → 注入 → 统一入口红报告 capture → 红报告 + 实际退出码 + 上下文喂 `repair-map` → 草案 → 用户具名确认（allowed_files/objective/reproduce/acceptance 一次核对）→ 恢复注入行 → 同命令绿 capture；同命令红绿链、observed_at 严格递增、账本密封。
- **CI 面不动**：L08 终态工作流与门规格保持原样；本讲远程复验缺口如实声明，留后续检查点统一裁量。

## Testing Decisions

- **好测试只测外部行为**：经公开接口断言 stdout JSON、退出码、输出文件内容与红绿链，不断言内部结构、不绕入口直调（仓库测试口径：工作台行为类测试经 CLI/独立 main 真实子进程运行）。
- **接缝（已具名确认）**：`bin/wb repair-map` CLI 子进程缝为唯一新高缝（六边界/三态/协议校验/退出码矛盾全部经此面）；`CancelChecks` 独立 main 缝复用（净树全绿、注入树红点构成断言）；探针 python 子进程缝作为统一入口内部件被整面覆盖；注入装置以拷贝树 diff 断言（注入行唯一 + 幂等）。
- **测试模块**：映射器合同测试（三态 + 六边界 + 哈希失配 + 退出码矛盾 + 写集安全）、统一入口合同测试（九登记项 + 目标树红绿）、注入装置测试、起始红三面（映射器类缺席 / 命令未注册 / 统一入口 main 缺席——Java 编译不绑实现类，L06-java 教训承袭）。
- **Prior art**：L05–L08 evals 工具合同测试（子进程 + stdout 断言）、L07 quality-gate / L08 ci-evidence 的 REGISTRY 命令测试、golden 六重放全量回归门、L08 InjectDefect 锚点唯一性测试。

## Out of Scope

- L10 修复 Loop（多轮返工、预算、停止条件、尝试记忆）——本讲 `max_attempts` 恒 1。
- 上游 `agent/` 模块家族其余件（agent_loop / agent_planner / agent_roster / subagent_coordination 等）——按讲渐进复刻，L09 只建修复映射件。
- 正式 `SalesService.cancel` 的修复——客户实现已在场且正确，本讲只加回归护栏登记项。
- CI 工作流与门规格改动（D8 裁定保持 L08 终态）。
- 上游 `assets/latest/candidate-*` 原始 JSON/diff 的补采或检查点显式采纳（pin 内缺席如实记录，留检查点处理）。
- Python 时代已退役能力的复活（对照源 = tag `python-carrier-final`，机检护栏在 L02 合同）。

## Further Notes

- **三层成功分离**是本讲证据纪律的核心：草案生成成功 ≠ 候选复验通过 ≠ 负责人接受；映射器与检查都不代签（铁律 2）。
- erp_increment 的"修复"表达为移除教学注入（恢复原行）——客户实现本就正确，注入是教学装置非真实事故，语义等价、形态差异如实记录（L08 先例直承）。
- 执行节奏：候选分支 `lesson-09`，commit 1 = 合同测试起始红 + 红证据；实现转绿前待用户显式 `/mattpocock-skills:implement`；修复链草案出来后有一次用户具名范围确认（配合点，一次列全等一句）。
