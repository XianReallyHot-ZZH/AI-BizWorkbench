数据模型（.runtime/course/L01-workbench/workbench.db）

表关键列存在理由
workbenchowner, name, version（仅一行）身份；同 owner 幂等，异 owner 拒绝覆盖
projectsproject_id（主键）任务必须有已登记项目（不留孤儿）
tasksrequirement_snapshot（全文）+ sha256快照语义：原文件再改，任务记得当时版本
evidencephase, command_text, output_text+sha256, returncode, observed_at只追加；失败与成功同等永久
phase 取值：red / diff / green / observation。前三相参与链判定，observation 是旁证。

五命令与失败纪律（接口冻结：上游 WORKBENCH_SPEC §5）

命令正常路径失败时
workbench-init建身份行异 owner 拒绝；同 owner 幂等返回既有身份
workbench-project-add登记项目重复编号拒绝，不覆盖
workbench-task-create建任务+抄快照缺项目 / 重复编号 / 文件不可读 → 拒绝且不留半条
workbench-evidence-add追加运行记录缺时区 / 空输出 / 任务不存在 → 拒绝且不留半条
workbench-status查询+完整性+摘要复核绝不建库建目录；对象缺失报 required_*_missing

链判定三规则（_chain_error）

#规则杀死的作弊形态
一存在同 command_text 的 red(rc≠0) 与 green(rc=0)换个命令跑绿来配旧红
二有一条成功 Diff 的时间严格介于该红与绿之间没改代码就宣称"改完转绿"
三全局最新的 red/diff/green 记录必须是成功绿（observation 不参与；绿后任何相出新失败即失权）拿旧绿灯给现在的坏状态翻旧账
红的判定是存在性的：早期红 + 其后 Diff + 绿也算完整（不必是"最新红"）。出处：上游 _chain。

防伪机制

机制一句话
摘要复核status 每次重算 SHA-256 对账，改库即报 *_digest_mismatch
失败不可抹退出码原样存原样返，无任何"由红改绿"路径
查询不建数据四个读命令在库缺失时报"尚未初始化"，绝不偷偷初始化
人审不代签evidence_complete 与 acceptance: pending_human_review 互相独立——材料完整 ≠ 有人接受；limitations 字段声明程序不能证明什么

术语对照

词面含义
same_command_red_diff_green_missing错误词面：缺同命令红—Diff—绿链
required_task_missing / required_project_missing要求存在的对象不存在
spec_digest_mismatch / output_digest_mismatch存储内容与摘要不一致（疑似篡改）
pending_human_review材料完整、等待人工审核（程序不代签）
自举（bootstrap）用刚建好的工作台记录它自己的建设过程
