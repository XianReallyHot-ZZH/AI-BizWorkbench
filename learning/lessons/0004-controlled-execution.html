受控执行：笼子怎么关住造笼子的物种

L04 的意图、机制与代码实现 —— 信任不是声明出来的，是被笼子拦出来、拦不住时被账本记出来的

为什么补这一课

你刚验收了 L04——A/B 双票、双具名验收门。但验收人最危险的时刻是亲手放行了什么都没看懂的东西。L04 的交付物（workbench/execution.py，三个新命令）在你仓库里只活了半天，就被真实使用抓出三处接缝缺陷：接口收参数被 -X 吞掉、预算缺声明不拒绝、spawn 失败裸崩丢记录。这一课的目标：下次看这类代码，你能自己指出"这道门防什么、防不住什么、失败了账本记什么"。

意图：能读合同 ≠ 能组织执行

L01–L03 依次交付了记账、守规、读合同。但让工作台念一遍 FDE_SPEC.md，库存导出不会自己发生——从"合同在场"到"代码交付"中间的每一步都可能走样：执行器进错目录、顺手改了无关文件、把失败说成完成、把 eval 绿说成验收。L04 把这中间过程交给了两票：

Ticket A（建设）Ticket B（交付）
谁监督人会话直接监督 Claude已具名接受的 V0 组织执行器
对象工作台自身（造笼子）flowERP 候选内的库存导出交付
验收门A 具名接受，才准启动 Bprobe 六场景 + 具名验收
自举递归A 造的笼子，关的正是造笼子的同一个物种（Claude Code）。这不是段子而是设计约束：笼子对"自己人"必须同样有效，否则它只防外人。L04 实测恰好验证了这一点——三处缺陷全是 V0 被真人 operator 和真实执行器使用时暴露的，不是测试想出来的。

机制：执行器合同五要素 → 状态机

ADR-0002 说执行器合同与上游同形：写集、预算、JSON 事件流、沙箱边界、退出码。落到 V0，每个要素都有"事前声明 + 事后实测 + 如实限制"三层：

要素事前（拒绝启动）事后（实测留证）如实限制（防不住什么）
写集code 模式缺 --write-scope 拒启动候选 git status --porcelain -uall 逐文件比对，越界 → out_of_scope、eval 前停止提示词约定防不住全部越界；不自动回滚（停止推进 ≠ 还原）
预算--execution-timeout 必须显式（缺 → 拒）超时 → timed_out 标志 + 部分输出保留—
事件流—claude -p --output-format stream-json 全量落 stdout 封 SHA-256约 1.5MB 未逐事件人工审读
沙箱cwd=候选、无起点提交拒收change_manifest 逐文件字节指纹候选是普通目录不是容器——事后抓，不事前锁
退出码—rc、eval_returncode、eval_timed_out 分立记录rc 0 ≠ 业务正确（本讲真实发生过）

所有执行结局汇入一条只派生、不存储的状态机（账本只追加，状态永远是记录事实的函数）：no_execution → review → accepted/rejected，失败态（failed / timeout / out_of_scope / eval_failed）原样即状态。三道门-guard：review 态拒绝重跑（不毁待审）、自批拒绝（复核人 ≠ 最近执行者）、前置门（B 单创建须绑定已具名接受的 A 单，拒绝不静默链接）。review 之后源码再变？新执行存在即旧复核自动失效——复核只覆盖它引用的那一次执行。

代码实现：三段真实代码，三个真实教训

全在 workbench/execution.py（419 行）与 bootstrap.py 状态推导里。每段代码后面跟着它为什么长这样——三个教训都是本讲当天真实发生的：

① _cmd_task_run 的门序：校验不落账，执行必落账

# 事前校验区：任一失败 → return _fail(...)，不产生任何记录
if args.mode == "code":
    if not scope:                  return _fail("write_scope_required: …")
    if executor_command is None:   return _fail("executor_command_required: …")
if args.execution_timeout is None: return _fail("execution_timeout_required: …")
if _task_state(conn, args.task_id) == "review":
                                   return _fail("task_in_review: …")

# 执行区：任何结局都走 _insert_execution 落账
outcome = _run_process(...)        # spawn 失败也返回 outcome，不抛异常
if outcome.timed_out:         record["status"] = "timeout"
elif outcome.returncode != 0: record["status"] = "failed"
elif out_of_scope:            record["status"] = "out_of_scope"   # eval 前停止
else: eval → "completed" / "eval_failed"
_insert_execution(conn, record, actor=args.actor)  # 兜底：记录必落
真实教训：B 票首跑，执行器 claude -p 已在候选内完成交付，但 eval 解释器路径写错 → spawn 的 FileNotFoundError 裸崩成"内部错误"，崩在插入之前，执行记录尽失。修复：_run_process 捕 OSError 返回"启动失败"outcome（test_launch_error_preserved_as_failed_record 先复现红再转绿）。门序本身就是答案：校验类拒绝不污染账本；执行类失败必须入账。

② _collect_changes：事后实测，字节指纹

raw = _git(ws, "status", "--porcelain", "-z", "-uall")  # -uall：新目录不折叠
_git(ws, "add", "-N", ".")          # 意图添加：未跟踪文件进 diff（仅索引标记）
diff_text = _git(ws, "diff", "HEAD").stdout
before = sha256(git show HEAD:path 的原始字节) if 在 HEAD else None
after  = sha256(工作树文件的原始字节) if 文件在 else None
两个细节都是修出来的：-uall——不加则新目录被折叠成 ?? dir/，manifest 会把里面每个文件误记成 deleted；指纹对原始字节而非 decode 后文本——否则编码同形的篡改能从 status 复核眼皮底下溜走。注意双轨口径：manifest 对字节（保交付物指纹），stdout/stderr/diff 摘要对账本内文本（防手改账本）。

③ _task_state：复核按 execution_id 匹配，不比时间戳

execution = _latest_execution(conn, task_id)
if execution is None: return "no_execution"
review = _latest_review(conn, task_id)
if review and review["execution_id"] == execution["execution_id"]:
    return "accepted" if review["decision"] == "approve" else "rejected"
return "review" if execution["status"] in COMPLETE else execution["status"]
第一版曾用秒级时间戳跨表比"最新"——同秒内新执行与旧复核并列时旧接受误判有效（合同测试抓出）。正确语义一句话：复核只覆盖它引用的那次执行；新执行存在，旧接受即失效。这就是"A 接受后源码又变，旧接受不再覆盖当前版本"的机器落点。
