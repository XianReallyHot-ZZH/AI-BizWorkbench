Lesson 0005 · 支线 S01 复盘

记忆系统：让工作台自己记得住教训

S01 的意图、机制与代码实现 —— 经验不进账本就等于没发生过，进了账本还要能被证明"没被改过、没过期"

为什么补这一课

你刚以六个具名动作验收了支线 S01（approve / publish / bind / outcome / v2 发布，全落你的名字）。但按本仓库的老规矩：放行了什么，就要读懂什么。这一课回答你点的四个问题：S01 在做什么？目的是什么？解决什么问题？代码怎么实现的？学完的标准：下次看记忆相关代码，你能自己指出"这条经验凭什么进账、凭什么被信、凭什么算失效"。

先看一个对照L04 的三条 claude -p 硬教训，昨天存在哪？交接文档的正文里——它随会话结束而蒸发，下一个 Claude 会话根本看不到它。今天它存在于哪？ASSET-becd3ae6，主账里的一行，带来源引用、带 SHA-256、会出现在下一次相关任务的召回里。同样的内容，两种存在方式，一个会蒸发，一个不会。S01 做的就是这个搬运——但搬运的每一步都有门。

意图：解决"经验蒸发"

上游 AGENTS.md 有一段逐字口径（调查笔记 §5 引）："单次交付成功、事件持久化、反馈登记或资产登记，均不足以证明三者已闭环。完成须有跨事项证据：前一事项经验被后一事项召回……"。翻译一下：工作台三件套 = Harness + 记忆系统 + 工作流蒸馏，L01–L04 建好了第一件，但当时的教训只能靠人肉搬运（交接文档、讲义、你的记忆）。换挡点之后工作台要"组织协同"，一个不记得自己犯过错的协调者，每次协作都从零开始犯同样的错。

所以 S01 的目的就一句话：把"已验收任务的经验"变成可治理、可召回、会失效的账本资产。注意三个限定词，各对应一道门：

限定词解决什么问题对应的门
可治理AI 自己提炼、自己发布、自己采用 = 既当运动员又当裁判具名人工审核（human() 词面拒绝 AI 名义）+ 非提炼者自审拒绝 + 跨项目治理拒绝
可召回账本里的死数据不叫记忆，能在新任务里被有理由地捞出来才叫关键词命中带理由、召回包整包落库、检索不到如实为空
会失效经验会过期；过期经验继续被注入比没有记忆更危险撤回/被替代只做状态迁移不删除；失效条目不再进召回，但全部历史保留

机制：五表、两套链、一条状态机

workbench/learning.py（770 行，七命令）背后是五张只追加的表（与上游同形，DDL 单一来源在 bootstrap.py 的 _LEARNING_SCHEMA）：

表装什么一句话职责
learning_assets记忆条目本体 + 冻结 payload + sha256经验内容（family+version 成版本链）
learning_eventscandidate/approve/publish/revoke/superseded 事件条目的只追加履历
learning_recalls每次召回的整包快照（RECALL-*）证明"当时召回什么、为何命中、为何排除"
learning_bindings采用快照（BIND-*，plan/task 双唯一）一次交付用了哪个版本的全文封存
learning_runs五相位证据，UNIQUE(binding_id,phase)采用之后的复验链
两套链的分工（本课核心判断）0001 课学的四相位红绿链没有消失，但它只服务任务证据账。记忆账用的是另一套：sha256 快照链。为什么分家？红绿链回答的问题是"这些记录的时序对不对"（红先于绿、diff 居间）；快照链回答的是"这份内容还是封存时的那份吗"。记忆的核心恐惧不是时序错乱，是内容漂移——所以每条内容都算哈希、每次读取都重算比对。记住这个分工：相位判时序，快照判不变。相位常量也分家了：记忆复用链自有五相位 precheck/implement/eval/review/outcome（learning.py:73），bootstrap.PHASES 四相位一个字没动。

条目生命周期是一条只派生不回改的状态机：candidate →(approve→publish)→ active →(发布新版本原子置)→ superseded，或 →(revoke)→ revoked。所有状态变更只改 state 列 + 追加事件，payload 和快照永不改写。

代码实现：四段门，四个真实故事

挑四段最值得读的。每段都对应一个 S01 真实发生过的故事——不是教学虚构。

① 来源准入：门在入口（learning.py:248）

def _admission_snapshot(conn, task_id, project_id) -> dict:
    task = _check_task(conn, task_id)          # 任务不存在 → required_task_missing
    if task["project_id"] != project_id:       # 跨项目 → project_mismatch
        raise LearningError(...)
    if _task_state(conn, task_id) != "accepted":   # 未具名接受 → source_task_not_accepted
        raise LearningError(...)
    execution = _latest_execution(conn, task_id)
    review = _latest_review(conn, task_id)
    snapshot = {...任务事实 + 复核 + 执行记录摘要列引用...}
    return {"task_id": ..., "snapshot": snapshot, "sha256": _sha256(_dumps(snapshot))}

只有 accepted 状态的任务能当提炼来源——而"accepted"不是一个人说了算的状态，是 L04 那套"执行 → 具名复核"派生出来的。经验从进入账本的第一刻就带着完整的责任链。封存的不是一句"来自 L04"，而是任务事实、复核人和执行记录指纹的整体快照 + 哈希。

② 读取即复核：信的是哈希，不是存储（learning.py:148-179）

def _check_payload_integrity(row, what):       # 每次读资产都走
    if _sha256(row["payload"]) != row["sha256"]:
        raise LearningError("memory_content_checksum_failed", ...)   # 快照被改动 → 拒读

def _check_source(conn, source):               # 来源引用链也复核
    for ref in snapshot["execution_refs"]:     # 与现账执行记录的摘要列逐一比对
        if ...摘要对不上...:
            raise LearningError("source_task_report_changed", ...)
真实故事复查轮发现 _check_source 读的是 source["execution_refs"]，而实际结构是 source["snapshot"]["execution_refs"]——循环体拿到空列表，整段复核安静地空转，返回码照常是 0。谁抓住的？合同测试 C5/C10：故意把来源执行记录连正文带摘要列一起改掉，show 却还成功。教训两层：复核代码自己也会错，所以复核必须被测试钉住"真的能拦"；而"安静地什么都不查"比报错更危险——失败不可抹的反面就是成功不可冒充。

③ 召回管线：每次"不命中"都有去处（learning.py:402）

for row in 项目的 active 资产:
    payload = _check_payload_integrity(...)    # 读时复核（②的门在召回里也过一遍）
    if 来源任务 == 当前任务:  → excluded["self_source:同源事项不得作为独立复用"]
    if 命中 excludes:         → excluded["excludes:..."]
    if 关键词不命中 applies:  → 静默跳过（检索面之外，不进任何分组）
    超出字符预算:              → excluded["budget_exceeded:..."]
    否则 → matches（带命中理由 applies:关键词）
conflict_key 相同的命中 → conflicts 分组，"请逐项判断，不自动合并"

整包（matches + excluded + conflicts + 预算占用）落库成 RECALL-*。检索不到就返回空 matches——不编造召回，这也是 C7 合同的断言。你验收时看到的两次召回就是这条管线：第一次命中 v1（RECALL-bc14883c），v2 发布后再召回只剩 v2——v1 不是被删了，是被状态过滤掉了。

④ 失效治理与防漂移：不删除，也不轻信（govern :331 / _validate_binding_assets :225）

# publish（govern 内）：同 family 旧 active 版本同事务原子置 superseded

for old in olds:
    UPDATE state = 'superseded'

# learn-run / learn-finish 开头：采用版本防漂移
def _validate_binding_assets(conn, payload):
    for asset in payload["assets"]:            # 绑定时封存的 sha256
        if 现账 sha256 != 封存 sha256:
            raise LearningError("binding_version_changed", ...)   # 复验前就拦下

两个"为什么"值得咀嚼：为什么失效不删除？与铁律 3 同构——删了失效记录，就删了"它曾经被认为是对的"这个事实，下次同样的经验再出现时无从对照。为什么绑定了还要再验？采用快照封存的是"当时的版本"，如果资产后来被改（哪怕哈希列一起被改），复验跑的就不再是当时采用的东西——C4 合同同时钉住了另一面：memory 类资产复用失败只记 outcome 不自动撤回（失败可能是用法错了，撤回是具名人工的判断）。
