Lesson 0006 · L05 复盘

缺陷基线：让检查自证清白

检查器辨别力三问 —— 全部素材取自你今天刚验收的 L05：无效探针、两连红、盲区实验、裸断言口径，没有一个是教学虚构

为什么补这一课

0004 课留的引子——「检查器自己会错吗」——你今天验收的 L05 就是正式回答。但这一课不是复述讲义：L05 执行期真实发生了一次翻案（讲义定稿被探针推翻重写），翻案本身恰恰是本课最好的教材。学完的标准：下次任何人对你说「检查都过了」，你能在三十秒内问出三个让绿灯自证清白的问题。

先看一个对照两份报告，都是绿的：报告甲——对干净候选跑检查，通过；报告乙——对干净候选跑检查，通过，且同一检查对已知坏版本连跑两次都报红。哪份证明检查有辨别力？甲只证明了「没报错」——它甚至可能根本没读到要害（今天真的发生了，见故事①）。乙才证明了「能抓住错」。上游 L05 辅导资料 §3 的原话：「检查在正确程序上通过，只能说明它没有报错。」

机制：辨别力三问

一份绿灯要自证清白，验收人依次问三个问题。每个问题对应 L05 的一道实证工序，缺一环，绿灯的效力就降一级：

三问问的是什么L05 的实证工序缺了会怎样
①检查谁？
（被测路径）		检查真的跑在它声称检查的实现上吗验证缺陷生效：打补丁后 on_hand 5→10、流水不重复，自检输出在案缺陷打在检查够不着的层上，红绿全是空转（故事①真实上演）
②抓得到吗？
（缺陷基线）		对已知带缺陷的版本，检查是否稳定报红同一命令对缺陷基线连跑两次，均 [BLOCK] rc=1（record 44/45）通过≠能抓错：可能检查太松、可能压根没执行到要害
③对什么盲？
（盲区对照）		检查读不到的状态里，藏着哪些它能放行的错账面重写实验：删旧流水键、写新键、库存返回正确——客户 eval 绿×2，驱动红（record 51）盲区被当成「已覆盖」，绿报告的效力被高估（C7 留痕就是防这个）
本课核心判断辨别力不是检查的属性，是检查×被测物这对关系的属性。同一个检查，对「重试再次入账」有辨别力（库存变了它就读得出来），对「账面重写」全盲（它从不读流水）。所以问「这个检查好不好」没有意义，要问「这个检查对哪一类错有辨别力」——而上游的验收标准把它钉成了一句可操作的话：「缺陷基线连续运行两次均失败；失败信息能够定位到具体要求。」

四个真实故事

① 无效探针：事实为真，层是错的（为什么第一问是「检查谁」）

讲义定稿 v1 现查过：客户 receive 已幂等，引用 inventory.py:102——这个事实完全为真。缺陷基线就照这条引用，把「重试多写流水」补丁打进了那一层。结果：客户 eval 连跑两次仍然绿。再查流水表：0 行。

真相：同一仓库里有两层幂等实现。eval 的用例走的是门面 ERPService.receive_stock（service.py:150，读写 inventory_events/stock 表），inventory.py:102 的 InventoryService.receive（stock_moves/stock_balance 层）它根本不经过。补丁打在检查不可达的层上，缺陷从未被触发，绿是货真价实的绿——也是毫无意义的绿。这次翻案把讲义推进到 v2：缺陷改打门面重放分支（重试再次入账），探针实证后才动工。

验收人用法「引用路径为真」和「被测路径为真」是两件事。看到证据账里写「X 已实现，位置在 F:L」，验收时多问一句：检查运行时真的会走到 F:L 吗？——本仓库的教训已经写进记忆：现查要查到被测路径级，代码阅读推断不算证据，动手前用探针实证。

② 两连红：两个「干净」和一个「同命令」

缺陷基线立起来之后，为什么非要连跑两次、还强调每次从相同干净数据开始？上游 §3 给了精确理由：「若第二次沿用第一次污染的数据，失败可能只是残留状态造成的，无法做同样的判断。」客户 eval 每次自建临时库，天然满足「干净」；连跑两次排除的是偶发（环境抖动、时序运气）。L05 的两条红（record 44/45，rc=1，[BLOCK]）+ 中间一条 diff（缺陷补丁，record 46）+ 一条绿（真实候选，record 48），构成完整链。

还有一处容易看漏的设计：红与绿是同一条命令。命令串逐字节相同（cd "$L05_EVAL_TARGET" && pwd && exec …），变的只是环境变量指向的树——红在缺陷基线，绿在真实候选。输出里的 pwd 行、封存的 argv、证据账三重披露。这正是 0001 课「同命令红绿」规则在本讲的变体：变的必须只有被测物，命令本身一个字都不能动——否则你无法排除「绿是换个跑法跑出来的」。

③ 盲区实验：绿灯的边界要亲手量出来

客户 eval 对「重试再次入账」报红——好。那它对别的坏法呢？造第四个探针：删掉原流水键、写入新键 receipt:001-rewritten，库存返回保持正确。业务上这比双入账更阴险：账面被重写了，数字却看不出问题。上游 §2 早就预言这类反例：「删掉一条旧流水、再多写一条新流水，数量没变，账却变了。」

实测：客户 eval 绿×2（它只断言返回值 on_hand 和 idempotent_replay，从不读 inventory_events）；同一棵树上，场景驱动一跑就红——{"step": "replay-ledger", "expected": "库存与流水均不变", "actual": "重放改变了账面"}。这就是三问的第三问：盲区不是缺陷，是边界——前提是它被如实写进证据账（L05 的 C7 留痕），而不是被绿报告盖住。为什么本讲不顺手给客户 eval 补上流水断言？因为那是改客户的检查——留待检查点显式采纳，本讲只留痕。

④ 裸断言：失败信息能定位到哪一层

上游验收标准还有后半句：「失败信息能够定位到具体要求」。L05 的红灯输出长这样：

[BLOCK] receiving_is_idempotent    122 ms  AssertionError:
{"total": 1, "passed": 0, "blocking_failed": 1, "decision": "block"}

断言消息是空的——客户用例用的是裸 assert，而 harness 的 error 载荷只有 {"type", "message"}，任何输出、任何报告都不会包含断言表达式本身。复查轮抓到证据账初版误称「traceback 行在场」，已纠正。最终口径是定位三件套：用例名（receiving_is_idempotent，名字即要求）+ [BLOCK] 行 + 数值级定位由 observing 驱动承载（expected on_hand 28 / actual 36 + 要求逐字文本）。顺带的收获：给客户 eval 加消息文本=改客户检查=违 D1，所以定位缺口用分层补足解决，而不是改检查凑口径。
