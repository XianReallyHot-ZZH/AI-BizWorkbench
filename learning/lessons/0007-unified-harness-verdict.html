Lesson 0007 · L06 复盘

统一裁判：让绿灯值得信

你的五个问题一次答完：解决什么问题 / 目标 / 方案 / 机制 / 代码解析 —— 素材全部取自你今天验收的 L06：假绿探针、可信红、R1 翻车、盲区实锤，没有一个是教学虚构

解决什么问题

到 L05 为止，每一讲都在造单个检查：幂等收货检查、范围检查、口径检查……L06 的问题是下一层——检查一多，谁来说「这次能不能交付」？五个检查四个绿一个红，交付还是拦截？谁数的结果？退出码给调用方的是什么？这些问题没有统一答案时，每个调用方自己数、自己判、自己解释退出码——数法不一致，结论就可议。

比没有检查更危险的东西上游 L06 辅导资料 §3 给了一段教学预期：
l06_stock_consistency：blocking，失败，查询 5、CSV 8
summary：blocking_failed=0，decision=pass
检查运行器退出码：0
分项发现了必须修复的错误，汇总却放行、退出码 0——假绿灯。没有检查，调用方至少知道自己在裸奔；假绿灯让错误交付披着可信的皮出门。所以本讲的第一目标不是「让检查变多」，是「让汇总没有资格撒谎」。

目标是什么

冻结合同 fixture 一句话：「统一 Harness、判决与退出码」。拆成三个可验收的承诺：①多项检查按登记清单跑，分级汇总出唯一 decision；②阻断失败、报告 decision、进程退出码三者一致（acceptance[1]）；③业务侧统一可用库存口径 available = on_hand − reserved 且永不为负（acceptance[0]，绑定 eval stock_never_negative）。还有一层不在合同字面上、在 LESSON_STORY 里：「统一等级、报告与退出码成为后续 Codex 交付的共同裁判」——L07 的 Hook 要在生命周期时点复用同一个入口，所以这个裁判必须是可复用的代码，不是一次性脚本。

方案是什么

客户真理现查再次改变形状：客户的 flowERP 已经自带统一 harness（eval/harness.py 的 run_suite：EVALS 登记 18 用例、blocking 分级、schema 1.0 报告、退出码 = blocking 失败数决定）。所以本讲不重写客户检查（同 L05 的 D1 裁决逻辑），增量落在本仓库：evals/harness.py（统一运行器：登记 → 分级执行 → 报告 → 退出码）+ evals/report_contract.py（报告一致性独立复核，review 缝）+ evals/l06/（登记项收口 + 口径交叉驱动 + 缺陷基线构造）。教学链照上游钉死的次序：先修汇总，再修业务——中停点的「可信红」恰好证明汇总修好了；跳过次序，最终变绿就说不清来自哪项改动。

设计了哪些机制

五个机制，每个都对着一种具体的撒谎方式：

机制防的是哪种谎落点
①分级：blocking / observing把告警升格成拦截（拦死正常交付），或把阻断降格成告警（放走坏交付）等级写在登记处（entries()），是事先确认的规则，不是跑完再定
②汇总自逐项推导假绿灯：summary 与 results 各说各话decision 和计数都从 results 现算，同一变量喂给报告和退出码
③报告独立复核（report_contract）谎报的 summary 骗过调用方复核器不信 summary，自己从 results 重推导 expected 再对质，连退出码一起核
④不吞错 + 报告独占崩溃吞掉后续检查；旧绿报告被新调用覆盖冒充异常记入该项 error 后继续跑；报告 open("x") 独占写，旧证据动不了
⑤客户真理 + 登记制裁判只认自家检查，或两套平行身份（L08 必撞）五登记项里两项直接子进程跑客户 blocking eval；报告 schema 1.0 与客户对齐，一套复核器两边通用
本课核心判断0006 课说「辨别力是检查×被测物关系的属性」；本讲补下半句：可信度是「逐项 → 汇总 → decision → 退出码」这条传导链的属性。链上任何一环自行其是（汇总不数分项、退出码不看 decision、复核只读 summary 不重推导），绿灯就断链。验收人看 Harness，看的不是代码多精巧，是这条链有没有暗门。

代码解析（四个文件，全部真实在库）

① evals/harness.py——七步解剖一个 run()

def run(entries, *, suite="all", names=None, report_path=None):
    if suite not in SUITES: raise ValueError(f"未知 suite：{suite}")   # 1 校验
    if len(registry) != len(set(registry)): raise ValueError("登记项重名")
    selected = [(n, l, f) for n, l, f in entries
                if n in requested and (suite == "all" or l == suite)]  # 2 选择
    if not selected or set(requested) != {n for n, _, _ in selected}:
        raise ValueError("选择为空、含未知项或与 suite 不匹配")        # 空跑不算过
    for name, level, fn in selected:                                   # 3 逐项执行
        try:
            evidence = str(fn()); passed = True
        except Exception as exc:                                       # 4 不吞错
            evidence = str(exc); passed = False
            error = {"type": type(exc).__name__, "message": str(exc)}
        results.append({..., "duration_ms": round(...)})
    blocking_failed = sum(1 for item in results                        # 5 汇总：唯一的真相源
        if not item["passed"] and item["level"] == "blocking")
    report = {..., "summary": {...,                                    # 6 报告
              "decision": "block" if blocking_failed else "pass"}}
    with target.open("x", encoding="utf8") as stream: ...              # 独占写
    return report, (1 if blocking_failed else 0)                       # 7 退出码同源

看第 5 步那一行 sum(...)：decision 和退出码都从这里这一个变量导出——汇总想撒谎，只能改这一行。假绿探针干的正是这件事：把这行挖成 blocking_failed = 0（上游同款缺陷），合同套件立刻两处红（test_02 0 != 1 HARNESS-BLOCK、test_04 HARNESS-ERROR）。九项合同测试就是给这条传导链的每一环上的锁：非多数表决（一败即 block）、observing 异常不升格、空选择拒绝、报告不可覆盖、消费端拒绝矛盾。

② evals/report_contract.py——复核器为什么骗不过

blocking_failed = sum(1 for item in results
    if not item["passed"] and item["level"] == "blocking")   # 自己重数，不读 summary
expected = {"total": len(results), "passed": ..., "blocking_failed": blocking_failed,
            "decision": "block" if blocking_failed else "pass"}
if any(summary.get(key) != value for key, value in expected.items()):
    raise RuntimeError("Eval 汇总与逐项结果不一致")
if returncode != (1 if blocking_failed else 0):
    raise RuntimeError("Eval 进程退出码与报告结论不一致")

关键设计：复核器把 summary 当被告不当当证人——期望值全部从 results 重新推导，再跟报告自带的 summary 当场对质；退出码也在同一结论下复核。它还先核用例身份（requested_cases 与调用方请求、与实际 results 三方一致，防「换了用例冒名跑」）。注意它和 harness 里那行 sum(...) 是两份独立实现——这不是坏味道，是故意的：复核若复用被复核者的代码，谎就能一起骗过两处。附带收益：schema 与客户 harness 同为 1.0，客户的报告也过了我们的复核器（record 69），L08「本地/远端同一 Eval 身份」的地基就在这。

③ evals/l06/checks.py——登记制与客户真理

def entries(opening: int, reserved: int) -> list[tuple[str, str, object]]:
    return [

        ("l05_receiving_regression", "blocking", (lambda: _customer_case("receiving_is_idempotent"))),

        ("l06_frozen_checks",        "blocking", _frozen_checks),   # 客户 eval 文件 sha256 对 vendors
        ("teaching_observation",     "observing", _teaching_observation),  # 教学告警

等级在登记处写死——这就是「事先确认的规则」。两项登记直接子进程调客户自己的 eval（L05 的幂等回归 + 本讲绑定的 stock_never_negative）：客户业务状态由客户检查说了算（ADR-0005），我们的裁判只负责收口不负责改判。目标树经 L06_EVAL_TARGET 环境变量注入——这正是链 B 红绿「同命令异树」的机关。
